# MOM Doc Organization

用于根目录 `docs/` 的统一文档组织。

## 适用场景

- 新增需求文档
- 新增设计方案文档
- 整理 skill 或 rule 来源说明
- 输出跨项目实施说明、排查说明或复盘文档

## 核心约束

- 文件命名统一使用 `序号-YYYY-MM-DD-HHmm-主题.md`
- 文档先建 `README.md` 索引，再按主题拆分
- 不写单个超长 Markdown 承载所有信息
- 说明来源、适用范围、维护方式
- 原始需求必须保留用户原文；截图、录屏、表格等附件放入 `00-原始需求/附件/`
- 新需求初始化必须携带用户原始需求原文；不得用“待补充”、占位词或助手总结代替原文
- `00-原始需求/` 必须完整留档，不得缩减；用户粘贴的长 SQL、脚本、接口示例、字段清单、验收要求、排除项、截图说明和附件留档状态都必须保留
- 附件必须保存到 `00-原始需求/附件/` 并建立相对链接；无法取得附件时必须记录“附件未落盘原因”和需要用户补传的路径
- 需求目录名必须包含可识别业务对象、页面、接口、报表或流程名称，避免“接口调整”“取数优化”等泛名
- 第一轮需求理解、范围判断或技术调查完成后，必须立即新增 `01-需求分析拆解/` 文件回写分析结论
- 第一轮调查后只更新 README 或进度文件、未新增证据化分析文件，视为文档门禁未完成
- 多轮迭代必须新增文件，不覆盖或重写上一轮分析、规划和进度
- 子目录不是摆设；阶段性任务完成时必须及时更新对应文件，保证换对话或上下文满后能从需求目录恢复
- 每次新增阶段文件后更新 `README.md` 的最新结论、产出物索引和迭代记录
- `README.md` 同时承担上下文索引职责，不再单独新建 `上下文索引.md`
- 产出材料统一放入 `04-产出物/`，不再使用 `中间文档/`
- 新增或重建需求 README、原始需求和阶段文件时，必须兼容 Tolaria：文件头使用 YAML frontmatter，第一行 H1 是 Tolaria 展示标题，文内使用相对 Markdown 链接为主，wikilink 作为关系和知识网络补充。
- Tolaria 兼容层不得替代现有 `task req` / `task project` 目录结构，不得把需求、分析、规划、进度合并为单篇笔记。
- Tolaria 元数据巡检使用 `task docs -- tolaria-check [<需求名>|--all]`；知识入库、Type/view 和需求知识索引发布使用 `task docs -- tolaria-publish <需求名>|--all`。

## 推荐结构

1. `README.md`: 目录导航、当前状态、关键规则、最新结论和验证方式
2. `00-原始需求/`: 用户原始描述、补充说明和附件
3. `01-需求分析拆解/`: 每轮分析新增文件
4. `02-任务规划/`: 按时间段新增规划文件
5. `03-开发进度/`: 每轮迭代新增进度文件
6. `04-产出物/`: SQL、MAGIC-API、前端说明、关联调查和附件

## Do

- 优先沿用现有编号风格
- 把原始需求、分析、规划、进度、产出物拆分到不同目录
- 启动需求时先落 `00-原始需求/`，分析后马上落 `01-需求分析拆解/`
- 原始需求按用户原文逐字留档；助手总结写到分析文件，不写成原始需求替代品
- 调查/口径确认后写分析，方案调整后写规划，实现/验证/联调/暂停/收口后写进度
- 每轮迭代新增文件，并在新文件里说明旧结论是否失效
- 为核心文档互相加导航链接或路径引用
- frontmatter 至少包含 `type`、`title`、`created`、`tags`；需求阶段文件额外包含 `requirement`，便于 Tolaria 按 type、属性、关系和 saved views 聚合。
- 中心 ETL 资产、需求产出物和阶段文件之间同时保留相对 Markdown 链接；可追加 `[[主题]]` wikilink 建立 Tolaria 关系。

## Don't

- 不要把所有信息写进一个文件
- 不要只写结论，不写来源和适用边界
- 不要覆盖上一轮分析、规划和进度文件
- 不要只初始化目录而不在阶段完成时写入有效内容
- 不要用助手总结替代用户原始描述
- 不要删减用户粘贴的 SQL、脚本、接口示例、截图说明或附件状态
- 不要新建 `成果物清单.md`、`上下文索引.md` 或 `中间文档/`
- 不要为了 Tolaria 展示效果改写既有目录层级、文件名编号或 `task` 生成入口
- 不要只写 wikilink 而缺少可在普通 Markdown/Git 查看器中工作的相对链接
