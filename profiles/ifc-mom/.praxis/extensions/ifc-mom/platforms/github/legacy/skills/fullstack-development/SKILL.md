# Fullstack Development

用于当前工作区下 lamp Java 后端与 apps/web-antd 前端联动开发任务的总控技能。

- 前端表单专项：`ifc-web-mom-max/.github/skills/frontend-form-development/SKILL.md`

## 适用场景

出现以下任一情况时使用本技能：

- 一个需求同时修改后端接口和前端页面
- 后端新增实体、VO、Query、Controller，同时前端补 API、类型和页面接线
- 需要做端到端 CRUD、详情、分页、状态变更、树结构、编码校验等完整闭环
- 需要先判断任务应该落在哪个 lamp 后端模块、apps/web-antd 前端目录，以及接口模型如何对齐
- 需要联调某个页面与某组后端接口，并检查权限、提示、国际化和事务边界是否一致

本技能不面向其它前端应用目录，也不处理脱离 lamp 架构约束的通用 Java/Vue 项目。

## 不适用场景

- 仅后端开发：优先使用现有 Java 后端专项技能
- 仅前端页面综合改造：优先使用前端通用开发技能
- 仅前端表单：优先使用前端表单专项技能
- 仅前端 API 建模与接线：优先使用前端 API 专项技能

本技能是总控 skill，负责：

- 判断任务落点与模块归属
- 先读取并拆解需求，再确定表设计与代码生成边界
- 决定先做后端契约还是先做前端接线
- 在需要时使用 PostgreSQL MCP 调查现有数据库表结构，避免重复建模
- 默认按当前工作区的单体启动方式设计，不预设微服务拆分
- 约束代码生成后的补齐范围，避免推翻生成骨架重写
- 在需要时切换到前端 API、前端表单、后端分层等专项规则
- 汇总最终联调、自检和交付说明

## 目标

输出结果必须同时满足以下要求：

- 先完成需求拆解、数据库设计和生成边界判断，再进入编码
- 后端遵循 Controller -> Service -> Manager -> Mapper 分层
- 前端遵循页面编排、API 定义、schema 组织、状态管理分责
- 前后端命名、字段、接口路径、分页结构、状态语义保持一致
- 不把后端 Entity 直接暴露给前端，不在前端重复造与后端冲突的模型
- 代码生成工具产出的前后端骨架优先延续，在其基础上填补缺失能力
- 前端 API 接线尽量复用现有模块与现有请求方法，不轻易新造重复接口
- 页面交互必须补齐权限、消息提示、国际化和基础类型约束
- 修改完成后至少给出一轮端到端自检结果

## 强制前置确认

开始编码前，必须先确认并记录：

1. 业务归属哪个后端模块，例如 mes、mdm、wms、qms、aps。
2. 前端对应哪个业务目录，例如 apps/web-antd 下的具体 views、api、store 路径。
3. 本次需求是标准 CRUD，还是包含状态、编码、树、批量操作、跨服务调用等扩展特性。
4. 后端是否已有相近实体、Controller、Facade、表结构或接口可复用。
5. 前端是否已有同域页面、API 文件、schema、hook、store 可复用。
6. 这是“后端先行、前端接线”，还是“按现有接口补前端页面”，或“两端同时设计”。
7. 是否按当前单体启动方式开发；若无特殊说明，默认按单体启动，不展开 cloud 兼容设计。
8. 是否需要先设计新表或调整已有表；若需要，优先调查现有 PostgreSQL 表结构。
9. Flyway SQL 文件应落在哪个迁移目录，是否直接修改代码生成的 SQL 文件。
10. 哪部分由代码生成工具负责产出，哪部分需要手工补齐。

若以上任一项不明确，先补齐信息，不要直接猜目录、命名或接口结构。

若任务跨越多个前端子领域，本技能负责总控拆分；若某一部分已经明显落到表单或 API 专项，则在该步骤内显式按专项技能规则执行。

## 总体分流规则

- 若需求尚未拆清，先停止编码，先做需求拆解、功能边界和数据落点确认。
- 若涉及新增表或改表，先做数据库设计，并尽量通过 PostgreSQL MCP 调查现有表结构与命名模式。
- 若你将先使用代码生成工具生成骨架，则先把生成输入准备完整，再对生成结果做增量补齐。
- 若任务主要是接口与数据库能力落地，先以后端为主线推进，再补前端接线。
- 若任务已有稳定后端接口，先锁定前端 API 模型，再推进页面实现。
- 若任务同时涉及页面、表单、API 和后端模型，按“后端契约 -> 前端 API -> 前端页面”的顺序推进。
- 若前端部分明显集中在表单或 API 细节，应显式套用前端专项技能约束，不要在总控技能里模糊处理。

详细执行步骤与分支判断见 [flow.md](./references/flow.md)。

## 标准实施流程

### 1. 先读取并拆解需求

先把需求拆成下面几类：

- 业务目标与核心流程
- 涉及的后端模块与前端页面范围
- 是否需要新增表、改表或补索引
- 哪些内容可以交给代码生成工具
- 哪些内容必须手工补齐，例如复杂接口、联动校验、页面交互、权限与消息处理

若需求拆解后仍不清楚输入输出边界，不进入生成和编码阶段。

### 2. 设计数据表与数据落点

若需求涉及新表或改表，先做表设计。

推荐顺序：

1. 通过 PostgreSQL MCP 查询现有表结构、字段命名、索引与关联模式
2. 对齐现有模块的命名风格、主键策略、审计字段和状态字段
3. 直接在代码生成工具产出的 Flyway SQL 文件上调整建表、改表、索引和约束
4. 明确新表、改表、索引、唯一约束和外键或逻辑关联关系
5. 再决定后端 Entity、VO、Query 与前端模型边界

不要在没看过现有数据库结构的情况下直接拍脑袋设计表。

若无特殊说明，MES 模块的迁移文件默认落在 `ifc-mom-column-max/lamp-support/lamp-boot-server/src/main/resources/db/migration/mes/2026/03` 对应目录下，并直接操作代码生成的 SQL 文件。

### 3. 先定位模块与现成样例

先在后端找到最接近的模块、实体、Controller、Service、Facade、application 配置；再在前端找到同域 views、api、schema、route、store、locale 实现。

优先复用现有目录和命名方式，不要跳过同域样例直接新建一套结构。

### 4. 明确代码生成边界

在生成前先明确：

- 由代码生成工具负责生成哪些基础骨架，例如表对应的实体、VO、Query、Controller、前端基础页面和 API 文件
- 哪些部分不适合生成，需要人工补齐，例如复杂查询、聚合接口、跨服务调用、状态流转、特殊表单交互

生成后处理原则：

- 优先在生成骨架上增量修改
- 不随意推翻目录、命名和基础分层
- 若生成结果与现有模块风格冲突，优先向现有同域实现靠拢
- 默认按单体应用内分层补齐，不额外引入微服务远程调用实现

### 5. 明确接口契约与对象边界

先明确后端输入输出，再决定前端建模方式：

- 后端：Entity、SaveVO、UpdateVO、ResultVO、PageQuery、DTO
- 前端：Entity、SaveVO、UpdateVO、ResultVO、PageQuery 或页面消费模型

约束如下：

- 后端不直接把 Entity 暴露给前端
- 前端 Entity 必须与项目 API 规范一致，`int64` 一律建模为 `string`
- 返回类型要对齐真实业务结构，不额外发明通用包装类型掩盖问题
- 查询、保存、详情、状态变更、树操作等接口语义必须在两端保持一致

### 6. 先实现或补齐后端骨架

按以下顺序补齐后端：

1. Entity 与 VO/Query
2. Mapper 与 Manager
3. Service 与事务边界
4. Controller
5. 仅在明确需要跨模块抽象时再评估 Facade；当前默认按单体实现

后端必须满足：

- Controller 只做参数校验、请求转发和轻量逻辑
- Service 负责业务编排与事务
- Manager 负责单表能力与可复用的数据访问能力
- Mapper 只做数据库访问
- 业务异常使用项目既有异常体系
- 查询避免 N+1、循环查库和无分页大查询

### 7. 再实现或补齐前端 API 与类型

后端契约稳定后，再补前端 API：

1. 在同域 `src/api` 下定义请求方法
2. 建立 Entity、VO、ResultVO、PageQuery 等类型
3. 使用现有 `requestClient` 风格接线
4. 校验字段类型、时间字段、枚举、数组、布尔和主键类型

前端 API 层必须满足：

- 导入路径统一使用 `#/`
- Entity 继承项目既有 `BaseEntity` 约定
- `int64` 不使用 `number`
- 尽量复用现有 API 文件、现有请求方法和同域模型，不轻易新增重复接口
- 页面直接消费标准 API 模块，不在组件内重复声明同类模型

### 8. 最后实现前端页面与交互

页面落地时保持单一职责：

- 页面负责编排
- schema 负责表单结构
- API 文件负责请求定义
- store 或 hook 负责状态与复用逻辑

同时检查以下方面：

- 列表、查询、详情、保存、删除、状态变更是否闭环
- 是否接入现有权限控制
- 是否使用统一消息提示或通知封装
- 是否接入国际化，避免硬编码
- 样式是否符合现有 Tailwind/BEM 组织方式

### 9. 联调与验证

至少做以下检查：

1. 后端接口路径、方法、参数、返回结构是否与前端调用一致。
2. 新增或修改的事务边界是否合理。
3. 前端提交、查询、详情回填、状态更新是否能闭环。
4. 错误提示、权限控制、空态和异常路径是否有基本处理。
5. 至少执行一类可行校验，例如 Maven 编译、前端类型检查、lint 或手动联调说明。

## 决策要点

### 何时以后端为先

- 需求依赖新表、新实体、新接口
- 页面行为受业务状态机或事务规则强约束
- 存在跨模块调用、Facade 或数据权限问题

### 何时以前端为先

- 后端接口已稳定，只缺页面展示与交互
- 需求主要是页面重构、列表整合、表单体验优化
- API 已存在，仅需前端消费和收口

### 何时需要跨服务设计

- 一个需求跨多个后端模块
- 明确要求额外抽象跨模块调用边界
- 当前模块只消费其他服务能力，不直接持有完整业务数据

当前工作区默认按单体启动处理；只有需求明确超出单体边界时，才评估是否补 Facade，而不是直接在 Controller 或前端中绕过分层。

## 输出顺序要求

执行此技能时，输出应遵循以下顺序：

1. 说明业务归属模块，以及前后端各自落点。
2. 列出计划新增或修改的后端类、前端文件和接口。
3. 说明是否涉及新表或改表，以及是否需要先通过 PostgreSQL MCP 调查现有表结构。
4. 说明哪些内容由代码生成工具产出，哪些内容需要手工补齐。
5. 说明关键分流判断，例如是否标准 CRUD、是否跨服务、是否需要表单/API 专项规则。
6. 再开始生成或修改代码。
7. 结束前给出联调与规范自检结果。

## 完成检查

- 后端目录、分层、命名、父类继承、事务边界正确。
- 涉及表设计时，已说明参考了哪些现有表结构或命名模式。
- 前端目录归属正确，路径导入使用 `#/`。
- 前后端字段、接口路径、分页/详情/保存模型一致。
- 代码生成结果被作为基础骨架复用，而不是无差别重写。
- 前端 API 已尽量复用现有实现，没有无必要重复接口。
- 前端没有把 API、页面、schema、权限、样式堆在单文件中。
- 页面已接入基本权限、消息提示和国际化。
- 至少完成一轮静态校验、编译校验或明确说明未执行原因。

提交前逐项复核可直接使用 [checklist.md](./references/checklist.md)。

## Do

- 先找同域样例，再开始改动。
- 先拆解需求，再决定表设计、代码生成和手工补齐边界。
- 涉及数据库时，优先用 PostgreSQL MCP 看现有表结构。
- 直接在代码生成后的 Flyway SQL 文件上做表结构调整。
- 先锁定后端契约，再接前端 API 和页面。
- 生成骨架后只补缺口，尽量不推翻生成结果。
- 把后端与前端修改范围明确列出来，避免边写边漂移。
- 对状态、编码、树、批量操作等特性做显式建模。
- 在结束前做联调路径和失败路径自检。

## Don't

- 不要跳过模块归属确认直接生成代码。
- 不要没看现有表结构就直接设计新表。
- 不要绕开 Flyway 目录，另起一套临时 SQL 维护表结构。
- 不要把代码生成工具能稳定产出的基础骨架全部手写重做。
- 不要把后端 Entity 直接当成前端返回模型使用。
- 不要在 Controller 里堆业务，或在页面组件里堆 API/schema/权限逻辑。
- 不要忽略 `int64` 到 `string` 的前端建模规则。
- 不要为了图快复制一套新 API，而不复用现有同域接口。
- 不要只实现一端却默认另一端一定兼容。

## 推荐提示词

- 为某个业务模块做一套前后端联动开发，后端补接口，前端补页面并完成联调。
- 基于现有模块新增一个端到端 CRUD，包含后端分层代码、前端 API、列表和表单。
- 检查这个需求的前后端实现是否符合项目规范，并直接修正分层、模型和页面接线问题。
- 按当前项目规范完成一个 Java + Vue 的全栈改造任务。
