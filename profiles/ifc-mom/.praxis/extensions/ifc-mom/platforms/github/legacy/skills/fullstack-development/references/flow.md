# 全栈执行流

本流程仅适用于：

- 后端为 lamp 风格 Java 分层项目
- 前端为 apps/web-antd
- 任务同时触及前后端，或需要由一个总控流程决定先后顺序与分流方式
- 当前默认按单体启动方式联调
- 当前默认模块为 MES，优先分组为 job

## 0. 先拆需求

正式编码前，先拆成四块：

1. 业务目标与功能边界
2. 数据表设计或改表范围
3. 代码生成工具负责的骨架范围
4. 需要人工补齐的后端接口、前端页面与交互

若第 2、3、4 项边界不清晰，不进入编码。

## 1. 先做落点判断

先回答四个问题：

1. 后端归属哪个 lamp 模块。
2. 前端归属 apps/web-antd 下哪个业务目录。
3. 本次需求是标准 CRUD、状态流转、树操作、编码校验，还是跨服务能力拼装。
4. 现有同域样例是否足够复用。

若这四项没有结论，不进入编码阶段。

## 2. 先看数据库，再定模型

若涉及新表或改表：

1. 先使用 PostgreSQL MCP 查看同域现有表结构。
2. 对齐字段命名、主键、审计字段、状态字段和索引习惯。
3. 直接修改代码生成后的 Flyway SQL 文件。
4. 明确哪些表是新增，哪些表是扩展，哪些只需要复用现有表。

不要跳过这一步直接反推 Entity 和页面字段。

## 3. 明确代码生成边界

在开始写代码前，先决定生成范围：

1. 哪些基础类和页面由代码生成工具生成。
2. 哪些复杂逻辑保留人工实现。
3. 生成后的代码哪些保留，哪些按现有同域风格修正。

原则：先生成基础骨架，再做增量补齐。

当前默认处理方式：

1. 后端和前端都按单体应用内目录补齐。
2. 不因为习惯问题提前引入 cloud 兼容分支。
3. MES 模块优先落到 job 分组既有目录。

## 4. 选择主线

### 后端优先

满足以下任一条件时，先做后端：

- 新增表、实体、VO、Query、Controller
- 页面行为依赖明确的业务状态机
- 需要 Facade、跨服务调用或事务设计

执行顺序：

1. Entity、VO、Query
2. Mapper、Manager
3. Service
4. Controller
5. 仅在明确需要跨模块抽象时再评估 Facade
6. 再进入前端 API 与页面

### 前端优先

满足以下任一条件时，可先做前端：

- 后端接口已稳定
- 主要是页面编排、交互、回填和展示收口
- 只需按现有接口补列表、详情、编辑或状态操作

执行顺序：

1. 确认接口契约
2. 前端 API 与类型
3. 页面、schema、hook、store
4. 联调和异常路径补齐

## 5. 前端专项分流

### 转前端 API 专项

出现以下任一情况时，显式套用前端 API 规则：

- 主要工作是 Entity、SaveVO、UpdateVO、ResultVO、PageQuery 建模
- 主要工作是 `requestClient` 请求方法编写
- 主要工作是把页面中的内联请求抽到标准 API 模块

### 转前端表单专项

出现以下任一情况时，显式套用前端表单规则：

- 使用 `useVbenForm`
- 需要 schema 拆分、回填、查看态/编辑态切换
- 需要 `zod` 校验或 `getValidateRuleByVben` 合并后端校验规则

## 6. API 复用优先

在前端 API 接线时，先检查：

1. 同域 API 文件里是否已有可复用方法。
2. 页面里是否已有内联请求可抽取复用。
3. 现有 ResultVO、PageQuery 是否已能覆盖当前页面。

只有现有 API 无法承载时，再新增请求方法。

## 7. 契约对齐顺序

无论先后端还是先前端，都按以下顺序校对：

1. 接口路径
2. 请求方法
3. SaveVO 与 UpdateVO 字段
4. ResultVO 与分页结果字段
5. 状态值、枚举、布尔和时间格式
6. 主键与 `int64` 字段的前端 `string` 建模

## 8. 页面接线顺序

推荐顺序：

1. 列表查询
2. 详情回填
3. 新增提交
4. 编辑提交
5. 删除/批量删除
6. 状态切换或其他业务动作

不要一开始就把所有交互混在同一个组件里。

## 9. 联调收口

至少完成以下收口：

1. 成功路径能跑通。
2. 常见失败路径有提示。
3. 按钮权限和只读态与后端规则一致。
4. 国际化和消息提示不缺位。
5. 至少执行一类校验：Maven 编译、前端类型检查、lint，或说明为何未执行。
