# 需求文档组织规范

## 目标

统一 IFC MOM 工作区需求类文档的目录命名、文件组织和迭代记录方式，确保原始诉求可追溯、分析规划可对比、产出物可复用，避免多轮迭代后文档漂移。

## 适用范围

- 本规范只适用于业务需求文档，即会形成业务功能、业务数据、业务页面、业务报表、业务迁移、业务联调或业务交付材料的需求。
- 根目录 `docs/` 下的需求目录只承载业务需求，不承载规则维护、流程纠偏、环境配置、工具配置、执行策略调整或过程改进。
- 业务需求原始输入、截图、会议纪要和补充说明。
- 业务需求分析、任务规划、开发进度和产出物。
- 与业务需求直接相关的 SQL、脚本、前端说明、关联信息调查和临时验证结论。

## 禁止写入场景

- 非业务需求禁止写入 `docs/02-req/YYYY-MM/` 需求目录，也不得通过 `task req -- init`、`docs iter` 或手工创建需求目录绕过。
- 规则维护、流程纠偏、执行规范固化、环境配置、工具配置、脚本入口说明、插件/skill 配置、过程改进和 Codex 行为约束，只能写入 `AGENTS.md`、`.praxis/extensions/ifc-mom/rules/`、`.praxis/extensions/ifc-mom/skills/`、相关脚本/配置或根目录 `todo.md`。
- 对非业务需求的执行说明应直接在对话交付中给出；确需持久化时，选择对应规则文件或 `todo.md`，不创建需求 README、分析、规划或进度文件。

## 分级规则（P0/P1/P2）

### P0（必须）

- 根目录 `docs/` 下只承载业务需求，不承接规则、工具链、行为约束等过程类内容。
- 业务需求必须优先通过 `task req -- init <简短中文需求名> <用户原始需求原文>` 初始化。
- `00-原始需求/` 必须完整保留用户原文，不能“待补充”或摘要替代；长 SQL、脚本、接口示例、字段清单、验收要求、排除项、附件留档状态必须逐字保留。
- 完成首次理解后，必须新增 `01-需求分析拆解/` 迭代文件；老需求不允许直接覆盖旧文件。
- 新增业务文件后需回写 README 的“最新结论”和“迭代记录”。

### P1（重要）

- 需求名需包含可识别业务对象，出现“接口优化/看板优化”等泛名时要补充具体对象。
- 不在需求根目录直接加临时目录，专题按阶段目录或产出物目录归档。
- 每轮迭代结束需新增阶段文件并在 README 更新索引。
- 若上一轮结论失效，必须新增新文件记录失效路径与替代结论。
- 需求目录不必迁移历史文件；继续迭代优先新增，不合并重排。

### P2（持续优化）

- 将重复出现的需求模板项合并为统一模板（分析/规划/进度/产出物命名示例可持续裁剪）。
- 减少一次性重写，避免需求文件过载；阶段文件优先按新阶段追加。
- 运行时发现文档重复项可提交到 `praxis.projects.toml` 及规则文件联动修订。

## 总体原则

- 一个业务需求在 `docs/02-req/YYYY-MM/` 下对应一个独立目录，不将多份业务需求混放。
- 新建业务需求目录必须优先使用 `task req -- init <简短中文需求名> <用户原始需求原文>` 初始化；除非脚本不可用或会破坏已有成果，不手工创建标准目录。
- 业务新需求初始化时必须同步写入用户原始需求原文；不得以“待补充”、助手总结或口头记忆替代原文。
- 用户原始描述是需求追溯最高优先材料，不得压缩替代。
- 每次迭代只新增文件，不覆盖或重写上轮原始需求、分析、规划和进度。
- 文档更新需随任务推进持续同步，而非交付前集中补写。
- README 同时承担导航与上下文索引，不再新增独立上下文索引文件。
- 不再新建 `成果物清单.md`，产出物由 README 与 `04-产出物/` 承载。
- 需求文档和 ETL 资产必须兼容 Tolaria Markdown，但 Tolaria 只作为知识网络和检索增强层，不替代 `task req`、`task project`、`task etl` 生成的系统结构。

## 需求目录命名规则

- 月份目录格式：`YYYY-MM`
- 需求目录格式：`YYYY-MM-DD-需求名`
- `需求名` 优先使用中文业务名称，避免英文缩写和过度抽象命名
- 同一天有多需求时，目录名应清晰区分业务主题
- 需求名需包含可识别业务对象、页面、接口、报表或流程名称；如“看板 MagicAPI 取数逻辑优化”“接口调整”“页面优化”需补充具体对象。

示例：

- `docs/02-req/2026-04/2026-04-10-成品退货/`
- `docs/02-req/2026-04/2026-04-10-PDA扫码流程优化/`
- `docs/02-req/2026-04/2026-04-10-生产大屏重构/`

## 标准目录结构

每个业务新需求目录至少包含：

```text
docs/02-req/YYYY-MM/YYYY-MM-DD-需求名/
├── README.md
├── 00-原始需求/
│   └── 附件/
├── 01-需求分析拆解/
├── 02-任务规划/
├── 03-开发进度/
└── 04-产出物/
    ├── SQL/
    ├── MAGIC-API脚本/
    ├── 前端需求说明/
    ├── 关联信息调查/
    └── 附件/
```

说明：

- `README.md` 只做导航和上下文压缩，记录目标项目、当前状态、关键规则、验证方式、最新结论文件和产出物索引。
- `00-原始需求/` 保留用户原始描述、补充说明、会议纪要、截图说明和附件。
- `01-需求分析拆解/` 沉淀业务流程、对象关系、字段口径、状态流转、边界条件、项目落点和待确认项。
- `02-任务规划/` 沉淀实施范围、分阶段任务、依赖关系、联调安排、验证方式和交付策略。
- `03-开发进度/` 记录每轮实现进展、已完成项、阻塞项、验证结果和下一步。
- `04-产出物/` 存放可复制、可验证、可复用的交付材料。

## 文件命名与迭代规则

- 阶段文件统一使用 `序号-YYYY-MM-DD-HHmm-主题.md` 命名，例如 `01-2026-05-11-1430-第一轮分析.md`。
- 序号按目录内文件递增，使用两位数字，确保排序稳定。
- 主题使用中文业务语义，不使用 `final`、`new`、`tmp`、`v2` 等。
- 每次迭代新增文件；禁止将多轮内容持续追加或覆盖到同一文件。
- 原始需求、分析、规划、进度文件只允许补正明显格式/链接错误，内容纠偏必须新增文件。
- 不在需求根目录直接新增临时专题目录；新增专题应放入对应阶段目录或 `04-产出物/`。

## 分阶段目录规则

### 阶段性更新门禁

- 需求理解、业务口径确认、数据库/代码/页面调查完成后，必须新增或更新 `01-需求分析拆解/`。
- 实施范围、任务拆分、验证策略、用户负责事项或不做内容确定后，必须新增或更新 `02-任务规划/`。
- 每轮实现、SQL/脚本产出、配置调整、验证执行、联调反馈、阻塞解除或收口完成后，必须新增 `03-开发进度/`。
- 形成可复制产物时，必须写入 `04-产出物/` 对应子目录；若产物改变正式结论，同步回写分析、规划或进度文件。
- 每次新增阶段文件后，必须更新 README 的“最新结论”“产出物索引”和“迭代记录”。
- 阶段文件需包含当轮结论、来源或证据、未决问题、下一步；不得只写空模板或不可执行内容。
- 用户要求暂停、换对话、上下文接近上限或阶段任务已完成但暂不推进时，先写入 `03-开发进度/`。

### 00-原始需求

- 必须保留用户原始描述，包含原文、长 SQL、字段列表、约束、验收要求、排除项。
- 原始需求文件必须优先按用户原文逐字留档；助手总结只能作为后续分析文件，不能替代、压缩或改写。
- 粘贴的长 SQL、脚本、接口示例、日志、字段映射、截图说明或验收清单时，必须完整保留。
- 若用户携带附件，应放入 `00-原始需求/附件/` 并在原始需求文件中建立相对链接。
- 无法取得附件二进制时，必须记录“附件未落盘原因”和补传路径。
- 推荐命名：
  - `01-YYYY-MM-DD-HHmm-原始描述.md`
  - `02-YYYY-MM-DD-HHmm-补充说明.md`
  - `附件/01-YYYY-MM-DD-HHmm-截图说明.md`

### 01-需求分析拆解

- 每次需求理解、范围变更、口径纠偏、技术调查后都新增分析文件。
- 新分析必须说明与原始需求的对应关系，避免需求漂移。
- 分析文件需记录已确认口径、待确认项、影响范围、样例、数据或代码对象调查结论；不能仅有目录占位。
- 若前一轮分析失效，在新文件中说明失效原因和替代结论。
- 推荐命名：
  - `01-YYYY-MM-DD-HHmm-第一轮分析.md`
  - `02-YYYY-MM-DD-HHmm-范围纠偏分析.md`
  - `03-YYYY-MM-DD-HHmm-字段口径调查.md`

### 02-任务规划

- 任务规划按时间段组织命名；计划调整时新增文件。
- 规划文件应写清实施范围、修改边界、验证方式、用户负责事项和不做内容。
- 计划调整需新文件说明原因、替代方案、风险和验证变化。
- 推荐命名：
  - `01-YYYY-MM-DD-HHmm-实施规划.md`
  - `02-YYYY-MM-DD-HHmm-生产验证调整.md`
  - `03-YYYY-MM-DD-HHmm-联调前规划.md`

### 03-开发进度

- 每次迭代、联调、验证或收口都新增进度文件，不覆盖历史文档。
- 进度文件记录当轮状态、已完成项、阻塞项、验证结果和下一步。
- 进度记录至少覆盖：代码完成、验证命令执行、联调反馈、暂停前信息。
- 推荐命名：
  - `01-YYYY-MM-DD-HHmm-初始进度.md`
  - `02-YYYY-MM-DD-HHmm-联调进度.md`
  - `03-YYYY-MM-DD-HHmm-收口进度.md`

### 04-产出物

- 按产出类型创建子目录，不要求每项都创建全部目录。
- `SQL/`：积木报表 SQL、迁移脚本、菜单接口、字典脚本、新表/视图 DDL、造数脚本。
- `MAGIC-API脚本/`：MagicAPI 脚本、接口参数说明、返回字段说明；沿用历史目录时保持一致。
- `前端需求说明/`：页面、表单、按钮、权限、交互、字段展示说明。
- `关联信息调查/`：字典、枚举、主数据、对象关系、字段来源。
- `附件/`：除原始需求附件外的截图、模板、对照文件。

## README 使用规则

README 必须包含：

- 基本信息：需求名称、目标项目、当前状态、验证方式。
- 原始需求入口：链接到最新原始描述和附件目录。
- 最新结论：链接到当前有效分析、规划、进度文件。
- 产出物索引：按 SQL、MAGIC-API、前端说明、关联调查列出文件。
- 迭代记录：每轮新增文件的时间、主题和状态。

README 不承载完整正文，不长期堆叠多轮分析与计划。

## Tolaria 兼容规则

- 新生成或重建的需求 `README.md`、原始需求、分析、规划、进度文档，应在文件头写入 YAML frontmatter。
- frontmatter 至少包含 `type`、`title`、`created`、`tags`；阶段文件额外包含 `requirement`；项目化 README 可补充 `project`、`status`。
- 第一行 H1 是 Tolaria 展示标题；普通 Markdown 相对链接是主导航，必须保证 Git、IDE 和普通 Markdown 查看器可读；`[[wikilink]]` 用于 Tolaria 关系和知识网络。
- 需要分类、默认属性或展示约束时，创建或维护 `type: Type` 的类型文档；需要视图时在 `views/*.yml` 创建 saved view，不创建 JSON view。
- `task docs -- tolaria-check [<需求名>|--all]` 只生成 `.praxis/out/tolaria/tolaria-check.json`，用于发现缺 frontmatter、缺 H1、缺必要字段等问题，不修改 `docs/` 正文。
- `task docs -- tolaria-publish <需求名>|--all` 发布 Tolaria 基础 Type、saved views 和需求 `04-产出物/Tolaria知识索引.md`，用于把已具备价值的需求接入知识网络。
- 需求目录与中心 ETL 资产互链时，需求侧只维护 `04-产出物/ETL资产链接.md`，中心口径卡仍以 `docs/03-etl/` 为准。
- Tolaria check/publish 不得改变标准目录结构、阶段文件编号、原始需求保留规则和产出物归档位置；旧文档缺元数据时先报告，再按需求分批修复。

## 产出物规则

- 产出物若形成正式结论，需同步回归到分析、规划或进度目录。
- 二进制资料统一放在 `00-原始需求/附件/` 或 `04-产出物/附件/`。

### SQL 产出物规则

- 涉及积木报表 SQL、DDL、对象关联、模型设计、应用设计、菜单接口资源、字典脚本或迁移脚本，应统一放入 `04-产出物/SQL/`。
- 迁移产出物按类型拆分：新表 DDL、视图 DDL、菜单/授权 SQL、配置 SQL、迁移总稿。
- MagicAPI `.ms` 脚本放入 `04-产出物/MAGIC-API脚本/`，不得混入 SQL。
- 用户仅要求 `.ms` 时，只输出 `.ms` 与接口说明；不得额外生成 `magic_api_file` SQL，除非明确要求迁移。
- SQL 文件仅保留 SQL、注释和执行说明；复核结果与风险应放在 `.md`。
- 正式迁移前置于 `04-产出物/SQL/`，待中间产物确认后再入 Flyway 正式目录。
- 总稿允许保留，但涉及对象落地时必须按表拆分文件。
- 推荐命名：
  - `01-YYYY-MM-DD-HHmm-积木报表SQL.sql`
  - `02-YYYY-MM-DD-HHmm-新表DDL.sql`
  - `03-YYYY-MM-DD-HHmm-新视图DDL.sql`
  - `04-YYYY-MM-DD-HHmm-迁移脚本.sql`
  - `05-YYYY-MM-DD-HHmm-造数脚本.sql`
- 模型设计/应用设计 SQL 仅归档，不主动改写。
- 正式迁移禁止单一总脚本，必须按对象拆分。

### DDL 与关联信息规则

- DDL 字段注释统一为 `中文列名;补充说明`。
- 表注释使用“中文表名;补充说明”或等价中文表达。
- 关联信息必须区分字典、Java 枚举、主数据、业务表、业务事实字段。
- 关联文档除技术编码外，必须给出字典中文名或关联表中文名。
- 页面展示口径以中文名称为准，不直接展示技术编码。

## 老需求处理规则

- 老需求不强制迁移到新结构。
- 混乱需求可仅新增/修正 `README.md` 索引；不移动历史文件。
- 继续迭代时优先新增到既有阶段目录；无目录再按本规范新增。
- 不回写、合并或重排历史分析、规划、进度文件。

## 根目录约束

- 不在仓库根目录随意创建 `task_plan.md`、`findings.md`、`progress.md`。
- 若需过程性文件，放入对应需求目录并用业务可读命名。
- 需求文档组织规则以 `.praxis/extensions/ifc-mom/rules/` 为准，`docs/README.md` 只保留入口导航。

## 维护要求

- 新建需求目录时遵循本规范。
- 手工创建需求目录后应补跑同名 `task req -- init`，并修正模板态 `README`。
- 修改需求目录结构或命名后，同步更新本规则、`AGENTS.md`、`README.md`、`.praxis/extensions/ifc-mom/skills/global/mom-doc-organization/SKILL.md`、`scripts/codex/momlib/docs.py`。
- 单项目/单类规则不默认上提为全局规范。
