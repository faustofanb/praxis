# Praxis 工作流精简索引

## 定位

本文件是默认执行入口，只放可执行的最小流程和细粒度索引。主控入口是 `task ...`（`Taskfile.yml` 编排；未安装 `go-task` 时按本机平台安装，Windows 不以 Homebrew 为前置假设）。

引用格式：`文档 -> 小节 -> 条目`。冲突时以更具体的项目规则和用户明确要求优先。

## 语言策略

默认使用中文与用户对话。需求文档、分析、规划、进度和交付说明必须使用中文；代码、命令、路径、API 名称、日志片段和用户提供的原始引用可保留原文。用户明确要求其他语言时，以用户要求为准。

## 步骤闭环

每完成一个可独立确认的工作流步骤，回复末尾必须给出“推荐下一步”和 2-4 个可选工作流动作，标明推荐项；涉及提交、交付、清理、远程操作、生产数据或扩大范围时，等待用户选择后继续推进。

## 一句话流程

分类落点 -> 复用已有需求/工作树 -> 必要调查 -> 最小代码修改 -> 语法检查 -> 必要留档。交付、测试、全局校验和角色拆分仅在用户明确要求时展开。

## 按需加载

规范不全量加载；按以下顺序裁剪上下文：

1. **入口层**：`AGENTS.md`（路由 + P0/P1 硬门禁）。
2. **索引层**：本文件对应步骤（只读当前步骤条目）。
3. **任务层**：`task context -- --brief <project> <需求名>` 输出低噪声恢复摘要；完整 `task context -- <project> <需求名>` 只在复杂/恢复/交接场景展开主对话和角色上下文；`$PRAXIS_DIR/context/<project>-<需求名>.json` 为机器压缩包，Taskfile 默认 `$PRAXIS_DIR=.praxis/out/runtime`。
4. **恢复层**：需求 `README.md`、最新阶段文件、`task project -- preflight <project> <需求名>`。
5. **项目层**：`.rule/projects/<domain>/`、`.skill/projects/<domain>/` 由 worker 按落点读取。
6. **专题层**：报表读 `08-轻量ETL*` 与 `mom-lightweight-etl-report`；迁移读 `backend/07-数据库迁移*`；命令契约读 `mom-praxis-command-contract`；真实库调查读 `mom-database-investigation`；交付分支读 `mom-delivery-branch-hygiene`；Web/低代码/报表前端样例搜索读 `mom-frontend-pattern-search`；长上下文控制读 `mom-context-budgeting`。

机器路由索引：`.praxis/manifest.toml` 按任务类型列出 `rules`、`skills`、`commands`、`gates`；`.praxis/core.toml` 承载可共享阶段、风险通道、工具候选和跨平台策略；`.praxis/project-adapter.toml` 承载 IFC MOM 项目特异路径、项目 kind 与规则入口；`.praxis/templates/` 承载 rule/skill 生成模板。`task system -- check` 校验索引一致性，`task system -- praxis-profile` 校验通用平台与项目适配边界，`task system -- template-check` 校验 rule/skill 模板规范。

## 默认执行清单

条目按优先级排序；同一步骤内 P0 在前。

### 1. 判断任务落点

**P0**

- 先读 `praxis.projects.toml`，按项目短名、`label`、`description`、`aliases`、`path`、`kind` 判断目标项目与任务类型；MOM/AOTU 聚合根不是单一 Git 仓库，不能用当前目录替代目标项目根。
- 按 `AGENTS.md -> 任务路由` 判断项目与任务类型。
- 报表类优先 `.skill/global/mom-lightweight-etl-report/SKILL.md` 与 `praxis-workflow/08-轻量ETL报表工作流.md`。

**P1**

- 项目短名、细则入口：见 `AGENTS.md -> 任务路由`。
- 聚合根不是单一 Git 仓库：见 `04-需求文档与Worktree.md -> Worktree 与分支`。
- 业务需求优先使用 `task ...` 工作流入口；直接调用底层脚本或跳过 task 入口须在过程说明中写明原因。

```bash
task system -- check
task system -- index
task system -- praxis-profile
task system -- template-check
task project -- status <project>
```

### 2. 初始化需求上下文

**P0**

- 有原始需求、调查、SQL、实施说明或进度等需要保留时，才用 `task req -- init` 或 `task project -- start <project>`；必须完整保留用户原始需求原文。
- 新建前先搜索同名和同业务聚合的未完成需求。连续调整使用已有需求名启动，复用其目录和工作树；仅独立上线、独立验收或明确切分范围时新建。
- 非业务需求不写入 `docs/02-req/YYYY-MM/`：见 `05-需求文档组织规范.md -> 适用范围`；确需需求化跟踪时使用 `.praxis/requirements/`。

**P1**

- 需求名须含可识别业务对象；产出物默认正式版表述：见 `05-需求文档组织规范.md`。
- 未用统一命令时，交付说明须记录豁免原因与风险：见 `04-需求文档与Worktree.md -> 目录与初始化规则`。

```bash
task req -- init <需求名> <用户原始需求原文>
task project -- start <project> <需求名> <用户原始需求原文>
task context -- --brief <project> <需求名>
task context -- <project> <需求名>
task project -- preflight <project> <需求名>
```

### 3. 创建 Worktree

**P0**

- 所有代码类需求无论大小，凡涉及业务代码新增、修改、删除或生成，必须恢复或创建主任务 worktree：见 `04-需求文档与Worktree.md -> Worktree 与分支`。
- 从 `defaultBranch`（通常 `local`）创建；禁止对 PDA 默认使用 `develop` 作开发基座。
- 接手/恢复需求先查看已有工作树和需求目录；快速路径不运行 `preflight`。

**P1**

- 同一需求优先恢复已有 worktree；不存在时才用 `task project -- start <project>` 创建，默认路径为 `.worktrees/<project>/<YYYY-MM-DD-需求名>-dev/`。
- Web worktree 须同步被忽略的本地配置；交付说明列出路径。
- 创建或同步 worktree 前，目标主项目仓库若有未提交变更或未跟踪文件，立即暂停并报告用户；禁止自行 stash、restore、commit、手工绕过统一命令或基于旧 `local` 继续创建 worktree。
- 禁止破坏性分支切换。
- 分支职责：见 `04-本地开发与交付工作流.md -> 分支职责`。

**P2 — 非代码豁免**

答疑、只读调查、纯文档或规则维护且不改业务代码的任务可不建 worktree。涉及代码改动时不得以“微小修复”“单文件改动”作为豁免理由。

### 4. 调查与证据

**P0**

- 改 SQL/迁移/报表口径/字段映射等：必须先通过 dbx MCP 做数据库只读调查：见 `03-调查门禁.md`。
- 生产库须确认环境、范围、许可；大表禁止全表扫描。
- 有需要保留的调查产出时，写入 `01-需求分析拆解/` 或 `04-产出物/关联信息调查/`；无文档产出时在交付说明中保留简短结论即可。

**P1**

- 调查只覆盖当前修改所需的调用链、字段、样例与同域代码；不默认展开完整规范与样例清单。
- Praxis Code Graph、源码和文档仅作定位辅助。
- Web/报表需求在实现前必须完成同域规范与样例调查，至少覆盖页面目录、API 注释、导出能力、VxeGrid 布局、MagicAPI 写法；禁止等用户指出后才补规范。

### 5. 拆分与 Subagent

**P0**

- 默认不派发 subagent；主对话直接完成调查与代码修改。
- 只有用户明确要求并行或工作确实无法由主对话可靠完成时，才拆分并声明写锁。

**P1**

- 主对话职责、派发字段、worker 回报：见 `02-主对话与Subagent.md`。
- 角色协议：`.skill/global/mom-agent-workflow/SKILL.md`。

**P2 — 主对话可直接处理**

答疑、纯文档、极小规则改动、subagent 不可用或用户明确要求。

### 6. Code Graph 使用

**P1**

- 源码理解前先按 `praxis.projects.toml` 解析目标项目，再以该项目 `path` 或需求 worktree 路径定位真实仓库根；只在该仓库根检查 `.codegraph/`。
- 目标项目仓库存在可用 `.codegraph/` 时，可用 CodeGraph 定位；否则直接源码搜索，不自动检查或重建图谱。

### 7. 文档迭代

**P0**

- 只有产生应留档的分析、计划、进度或产出物时才新增阶段文件；不为快速代码修改创建占位文档。

**P1**

- 命名、增量迭代、纠偏新增文件：见 `05-需求文档组织规范.md`。
- 调查/规划/实现/验证后分别写 analysis/plan/progress。

```bash
task req -- iter <需求名> analysis|plan|progress <主题>
task req -- iter <需求名> analysis|plan|progress <主题> --body-file <阶段正文.md>
task req -- check <需求名>
task req -- index <需求名>
```

### 8. SQL 与迁移

**P0**

- 开发/调查阶段禁止直接改正式 Flyway；中间产物为唯一参考来源。
- 收尾且确认后才写入正式 Flyway：见 `backend/07-数据库迁移与Flyway规范.md`。

**P1**

- 报表按轻量 ETL 分层：见 `08-轻量ETL报表工作流.md`。

### 9. 验证

**P0**

- 业务需求默认只检查变更代码的语法或可解析性；不运行 TDD、测试、预检、check、命令审计或全局校验。
- 用户明确要求验证、或进入交付收口环节时，再按风险选择最小验证。

**P1**

- 验证等级 L0/L1/L2 与项目策略：见 `05-大任务拆分与验证.md`。
- Web/PDA 验证脚本发现 worktree 缺 pnpm 依赖时自动先执行 `pnpm install`；eslint 只扫描需求变更范围内仍存在的源码文件。

```bash
task project -- verify <project> <需求名>
```

### 10. 交付收口

**P0**

- 提交/交付须用户明确确认；`commit-split` 前 Quality PASS，`deliver`/`cleanup` 前 Quality + Delivery 均 PASS。
- 独立 Quality Agent code review，不能用 guard/编译/单测替代。

**P1**

- 标准链路：`status -> finish -> code review -> ready -> deliver -> status -> cleanup`：见 `06-交付收口.md`。
- feature 从 `upstreamBranch`（后端/Web 为 `develop`，PDA 为场景分支）创建，只 cherry-pick `finish` 生成并经复核的显式提交清单；本地测试辅助与临时验证提交默认排除。
- `deliver` 后必须做正式 feature 污染检查，发现测试文件、test-only `pom.xml`、临时验证或本地专用文件则阻断 push。
- 交付说明 5 项必填。

```bash
task gate -- ready <project> <需求名>
task gate -- validate-verdict quality <project> <需求名> $PRAXIS_DIR/verdicts/<project>-<需求名>-quality.json
task delivery -- status <project> <需求名>
task delivery -- finish <project> <需求名>
task delivery -- deliver <project> <需求名>
task delivery -- cleanup <project> <需求名>
```

`task gate -- guard|change-check|migration-check` 保留为专项诊断命令；常规收口优先使用 `task gate -- ready`，避免重复扫描。

### 11. 过程改进

- `todo.md` 只记录过程改进；稳定项同步到规则/skill：见 `07-过程改进与维护.md`。
- 新增/改名脚本须同步更新文档与 `task system -- index`；涉及通用平台配置或项目适配时同步运行 `task system -- praxis-profile`。

## AGENTS.md 职责边界

`AGENTS.md` 只保留：定位、任务路由、P0/P1 硬门禁、常用命令、提问模板。

不在 `AGENTS.md` 复写：完整需求文档规则、subagent 细则、验证等级、交付规则、Flyway 细则——分别归对应 `.rule/` 文件，经本索引按需加载。
