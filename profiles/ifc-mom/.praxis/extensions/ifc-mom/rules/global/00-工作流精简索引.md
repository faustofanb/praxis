# Praxis 工作流索引

本文件是默认执行入口，只保留跨任务都需要的约束。细则按任务读取
`.praxis/extensions/ifc-mom/rules/global/praxis-workflow/` 和
`.praxis/extensions/ifc-mom/rules/projects/`，项目规则优先于全局规则。

## 基本策略

- 默认使用中文与用户对话；需求文档、分析、计划、进度和交付说明使用中文。代码、命令、路径、API、日志和原始引用可保留原文。
- 先解决当前请求，不为可能出现的需求预建抽象、文档、工作树或验证流程。
- 默认由主对话完成；仅在用户明确要求并行，或主对话无法可靠完成独立高风险工作时派发 subagent，并声明写入范围。
- 提交、交付、清理、远程操作、生产数据和范围扩张需要用户明确授权。

## 1. 定位项目和上下文

1. 读根级 `praxis.projects.toml`，按项目的 `label`、`description`、`aliases`、`path` 和 `kind` 定位真实项目根；MOM/AOTU 聚合根不是单一 Git 仓库。
2. 读 `AGENTS.md` 和匹配任务的项目规则。不要全量加载规则与技能。
3. 恢复任务时先用简报；只有复杂恢复或交接才加载完整上下文。

```bash
task context -- --brief <project> <需求名>
task context -- <project> <需求名>
task project -- status <project>
```

源码定位优先使用本地搜索。目标仓库已有 `.codegraph/` 时，可使用
`task system -- codegraph status|explore|query|impact`；图谱缺失时不自动初始化。

## 2. 决定是否建立需求与工作树

- 只有原始需求、调查、SQL、计划、进度或产出物需要留档时，才创建或复用需求目录。
- 新建前搜索同名未完成需求；同名可恢复，不同名称默认独立。
- 修改业务代码前创建或恢复目标项目 worktree。答疑、只读调查和工作流自身维护可豁免。
- 创建或同步 worktree 前若目标仓库有未提交变更，暂停并报告；不得自行 stash、restore 或提交。

```bash
task req -- init <需求名> <用户原始需求原文>
task project -- start <project> <需求名> <用户原始需求原文>
```

需求组织和 worktree 细则见 `praxis-workflow/04-需求文档与Worktree.md`。

## 3. 调查和实现

- 调查只覆盖当前变更所需的调用链、字段、样例和同域代码。
- SQL、迁移、报表口径和字段映射变更先做获准的数据库只读调查；生产库须确认环境、范围和许可，大表禁止全表扫描。
- 调查结论需要留档时写入需求目录，否则在交付说明中给出简短证据。
- Web/报表实现前确认同域页面、API、导出、表格布局和后端写法。
- 迁移开发阶段先维护中间产物，确认收尾后再写正式 Flyway。

数据库门禁见 `praxis-workflow/03-调查门禁.md`；迁移规则见
`rules/projects/backend/07-数据库迁移与Flyway规范.md`。

## 4. 验证

- 默认执行与变更风险相称的最小代码级检查：diff、语法/解析、lint、类型检查、编译或聚焦测试。
- 浏览器/UI、外部联调、完整回归、独立 Quality 复核和收口门禁仅在用户要求或进入获准的交付阶段时执行。
- 不用页面可见效果替代可重复的代码证据。
- 后端通过 `task project -- verify` 执行增量编译；除发布本地制品或跨仓库联调外，不手工执行根级 `mvn ... -am install`。
- 生产代码最后一次修改后执行一次项目验证；之后只改测试时重跑相关测试即可。

```bash
task project -- verify <project> <需求名>
```

验证等级和项目命令见 `praxis-workflow/05-大任务拆分与验证.md`。

## 5. 文档和交付

- 只有存在应留档的新信息时才新增阶段文件，不创建占位文档。
- 提交或交付前展示变更、验证证据和残余风险，等待用户确认。
- `commit-split` 前需要 Quality PASS；`deliver` 和 `cleanup` 前需要 Quality、Delivery PASS。
- 常规收口使用 `status -> finish -> review -> ready -> deliver -> status -> cleanup`。

```bash
task req -- iter <需求名> analysis|plan|progress <主题>
task req -- check <需求名>
task gate -- ready <project> <需求名>
task delivery -- status <project> <需求名>
task delivery -- finish <project> <需求名>
task delivery -- deliver <project> <需求名>
task delivery -- cleanup <project> <需求名>
```

交付细则见 `praxis-workflow/06-交付收口.md`。

## 6. 工作流维护

- 人工入口只使用分组命令：`task req|docs|project|context|etl|gate|role|delivery|system -- ...`。
- 配置和规则变更运行匹配的聚焦测试；同步配置时显式使用 `--prune` 才删除 profile 管理目录中的陈旧文件。
- 稳定改进直接更新对应规则或 skill；不要维护重复的总索引。

```bash
task system -- check
task system -- index
task system -- praxis-profile
task system -- policy-check
task system -- template-check
```
