# 本地开发与交付工作流

## 目标

为当前 MOM 工作区统一本地开发基座与最终交付边界。

## 分支职责

### upstreamBranch

- 远端公共基线，配置来源为 `praxis.projects.toml`
- 新特性分支的起点
- 不承载个人本地配置和个人专用文档
- 后端/Web 通常为 `develop`；PDA/场景项目按配置使用对应场景分支，禁止泛化为 `develop`

### defaultBranch / local

- 本地长期开发基座，配置来源为 `praxis.projects.toml`
- 保持可运行、可测试、可联调
- 允许保留本地环境配置、开发脚本、本地 skill、个人文档、临时测试辅助
- 所有涉及业务代码新增、修改、删除或生成的需求无论大小，都必须从 `local` 创建需求 worktree，不直接在 `local` 推进业务代码改动
- 非后台前端项目的 `local` 应基于对应站点/场景基座分支，例如 `station/QMS/local` 基于 `station/QMS/base`；不得在未确认项目基座时默认改用 `develop`

### codex/*

- 本地需求 worktree/集成分支
- 用于具体需求开发、审阅和测试
- 命名使用简短中文需求名派生，例如 `codex/YYYYMMDD-需求名`
- 需求完成后不强制合并回 `local`
- worktree 默认集中放在工作区根目录 `.worktrees/<project>/<YYYY-MM-DD-需求名>-dev/`，避免分散到需求文档目录或污染业务项目 Git 状态

### feature/*

- 远端交付分支
- 只保留真正需要推送的业务改动
- 不混入本地配置、本地 skill、个人文档和临时验证代码

## 推荐流程

1. 开始新需求前，必须按项目配置同步 `upstreamBranch -> defaultBranch`（后端/Web 常见为 `develop -> local`）；统一脚本默认执行 `fetch + switch defaultBranch + merge --no-edit origin/<upstreamBranch>`，把上游更新合并进本地基座，冲突时失败并要求人工处理。
2. 使用统一脚本从 `defaultBranch` 创建需求 worktree：`task project -- start <project> <简短中文需求名> <用户原始需求原文>`；需求名必须包含可识别业务对象或页面名称，原文不得用摘要替代。
3. 启动后确认 `00-原始需求/` 已完整保留用户原文、长 SQL/脚本/接口示例和附件留档状态；第一轮需求理解后立即通过 `task req -- iter <需求名> analysis <主题>` 回写证据化分析拆解。
4. 在需求 worktree 完成业务开发、审阅和本地验证；不得因改动很小、只改单文件或只改文案而回到主项目仓库直接修改业务代码
5. 本地提交前先完成独立 code review，按变更落点引用对应项目规则，复核本次交付变更的业务口径、事务时机、异步边界、异常隔离、幂等、迁移配置和测试覆盖风险；不得用编译、单测或门禁输出替代 code review
6. 本地提交明确区分“本地内容”和“特性内容”
7. 交付前使用 `task delivery -- finish <project> <简短中文需求名>` 检查收口信息
8. `git commit`、`git push`、`git cherry-pick`、`deliver`、`cleanup`、删除 worktree 或删除分支前，必须先手动告知用户即将进入收尾并获得明确确认
9. 先确认需求提交已保留在本地需求 worktree，不删除、不改写已审阅提交
10. `task delivery -- finish` 生成 `.praxis/out/delivery/<project>/<需求名>/confirmed-commits.txt`，正式交付必须先确认该哈希清单；不得用“非 `test:` 提交”隐式筛选，`test-support:`、`local-test-support:`、临时测试和仅 test-scope `pom.xml` 依赖默认 local-only
11. 从最新 `origin/<upstreamBranch>` 创建 `feature/<中文简短需求名>`，优先使用 `git switch --no-track -c feature/<中文简短需求名> origin/<upstreamBranch>`，通过 cherry-pick 将确认清单中的特性提交收口到 `feature/*`；不得直接从 `defaultBranch/local` 切出交付分支，不把 `test:`、临时测试或其他不交付提交带入 feature
12. 常规收口使用 `task gate -- ready` 聚合 preflight/guard；`task gate -- change-check` 保留为专项诊断命令，并与 `task delivery -- deliver` 复用脚本门禁：生产提交消息必须是 `type(scope): subject` + 空行 + 编号明细；MES PAD BFF Controller 变更必须包含菜单授权 Flyway 迁移脚本
13. `deliver` cherry-pick 后必须检查正式 feature 污染：`src/test`、test-only `pom.xml`、临时验证文件、codex-only 文件或 local-only 提交一律阻断后续 push
14. 创建 feature 后立即执行 `git branch -vv --list feature/<中文简短需求名>`，确认不跟踪 `origin/<upstreamBranch>`；若显示跟踪关系，先执行 `git branch --unset-upstream feature/<中文简短需求名>`，推送时再显式使用 `git push -u origin feature/<中文简短需求名>`
15. 收尾阶段不默认运行编译验证；编译、统一分发或集成验证应在开发阶段完成，收尾只做分支整理、提交筛选、状态确认和清理
16. `feature/<中文简短需求名>` 已在主项目仓库创建并完成生产提交 cherry-pick 后，清理需求 worktree 和本地任务分支；清理后只保留正式 `feature/*` 分支，便于在主项目直接 checkout/push：

```bash
/usr/bin/git -C <需求worktree路径> status --short
/usr/bin/git worktree remove <需求worktree路径>
/usr/bin/git branch -D <codex/任务分支>
/usr/bin/git worktree prune
```

推荐使用统一脚本清理：`task delivery -- cleanup <project> <简短中文需求名>`。脚本默认清理 `.worktrees/<project>/<YYYY-MM-DD-需求名>*` 对应的已登记需求 worktree，删除本地 `codex/*` 开发分支；如历史交付流程遗留了正式 `feature/*` worktree 占用，也只解除该占用，不删除正式 feature 分支，便于主项目后续直接 checkout/push。

## 提交建议

- 本地内容建议使用前缀：`local:`
- 特性内容按类型和影响域拆分为：`feat`、`refactor`、`fix`、`chore`
- 生产提交标题格式为 `type(scope): 主要信息`，其中 `scope` 写业务或项目范围，如 `mes`、`web`、`pda`
- 生产提交标题后空一行，再按序号写主要改动明细
- 一个提交只做一类事情；同一需求同时包含新功能业务代码和既有功能接口命名/生成兼容修复时，必须拆成不同生产提交
- 提交消息必须符合项目模板且使用中文；`deliver` 会在 cherry-pick 前读取完整提交消息并硬拦截不规范提交
- `commit-split` 对存在 commitlint `scope-enum` 的项目必须在提交前校验 scope；scope 不在枚举内时直接阻断，不等 pre-commit hook 失败

## 风险控制

- `defaultBranch/local` 定期同步项目配置的 `upstreamBranch`
- Codeup HTTPS Git 操作优先使用 `task`/`rtk` 工作流入口；必须手工执行底层 Git 时先用 `rtk --version` 判断 RTK 是否可用，可用则使用 `rtk git ...`，不可用则使用 `/usr/bin/git ...` 并在交付中报告 `RTK optimization unavailable`，禁止裸 `git ...`。
- 需求 worktree 创建前必须确认目标主项目仓库干净并同步 `defaultBranch/local`；若主仓库存在未提交变更/未跟踪文件，立即暂停并报告用户，禁止自行绕过、stash、restore、commit 或基于旧 local 创建 worktree
- 所有业务代码改动必须在需求 worktree 内推进；答疑、只读调查、纯文档或规则维护且不改业务代码的任务可不建 worktree
- 若同步合并失败或存在冲突，不得继续创建基于旧 local 的 worktree
- 需求 worktree 直接用于开发、审阅和测试，不强制合并回 `local`
- 不把本地专用内容误带入 `feature/*`
- 新建需求 worktree 后默认设置 `git config core.quotePath false`；脚本解析路径时优先使用 `git diff-tree -z` 这类 NUL 分隔输出，避免中文路径被转义后误判
- 未得到用户明确收尾确认前，不执行提交、推送、cherry-pick、deliver、cleanup、删除 worktree 或删除分支
- 收口时优先按提交边界收口，而不是完全靠肉眼挑文件
- 用户明确说“直接收尾”时，停止新增需求文档、分析记录、README 索引等非代码产物；只做提交、创建 feature、cherry-pick、验证、状态报告，并说明已有但未进入 feature 的文档或过程记录变更。
- cherry-pick 冲突时先说明冲突原因和保留范围，再解决冲突；解决后运行冲突标记扫描和目标测试，需求文档、本地配置不得进入 feature。
- 清理需求 worktree 前必须确认提交已保留、正式 `feature/*` 分支已创建且工作树无未提交变更；清理后同步删除对应本地 `codex/*` 任务分支，只保留可推送的 `feature/*` 分支

## 适用边界

本规则适用于当前工作区的个人长期本地开发基座场景。

若未来仓库采用不同协作方式，应以实际团队流程为准。
