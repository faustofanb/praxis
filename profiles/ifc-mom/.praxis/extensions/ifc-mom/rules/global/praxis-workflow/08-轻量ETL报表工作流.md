# 轻量 ETL 报表工作流

## 定位

本规则用于 IFC MOM 工作区的报表、统计、驾驶舱、MagicAPI、积木报表和报表口径治理任务。

默认架构：

```text
PostgreSQL 函数沉淀规则
PostgreSQL 视图沉淀口径
MagicAPI 暴露接口
积木报表负责展示
```

这是一套逻辑 ETL / 虚拟数仓 / 轻量报表数仓方案，不默认引入新调度平台、物理数仓或报表库。普通 PostgreSQL 视图不物理保存结果，性能边界必须保守评估。

ETL 资产沉淀不以单次需求目录为长期唯一载体。需求目录负责保存原始需求、调查证据、决策过程和阶段记录；可复用的口径卡、函数/视图 SQL、对账说明、积木报表契约和 MagicAPI 薄接口建议，应同步沉淀到独立目录。新主题目录必须对应真实菜单层级：

```text
docs/03-etl/<应用>/<系统>/<一级菜单>/<二级菜单>/.../<中文主题>/
```

第一层 `<应用>` 必须先按顶部应用分类：`运营平台`、`基础平台`、`仓库管理`、`供应协同`、`生产制造`、`质量管理`、`设备管理`、`计划排程`。菜单编码写入 README/口径卡作为证据；目录层级使用菜单名称，例如 `生产制造/MES/04-工厂建模/06-班次信息/<主题>/`。旧的粗模块目录只作为历史资产兼容和迁移暂存，不作为新主题默认落点。需求目录中的产出物可保留副本或指针，但 README 必须指向中心 ETL 资产。

`docs/03-etl/资产索引.md` 是全局 ETL 资产台账，必须登记所有可复用 ETL 资产。单个需求或单个资产目录不得各自维护同名局部资产索引。资产台账至少登记：资产编码、资产类型、层级、状态、版本、主要函数/SQL、调用方、验证入口、性能方案、刷新/补算策略和备注。

这里的“资产”包括函数、视图、物化视图、汇总表、调用模板、口径卡和验证 SQL 等可治理工件，不只指物化视图。面向驾驶舱、高频刷新、跨月统计或大表聚合的场景，必须在实时函数、普通视图、物化视图和汇总表之间做性能方案选择，并写清刷新/补算策略。

需求目录和中心 ETL 资产的交付内容默认使用可直接复制到正式目录的正式版表述；除历史兼容目录外，新文件名、标题、状态字段、SQL 注释和 COMMENT JSON 不写“草案”或 `draft`。是否已落库由需求目录位置、中间产物路径、交付说明和收尾确认区分，不靠文件内容降级表达。

ETL 目录和主题资产优先用脚本初始化，避免手工目录漂移：

```bash
task etl -- init
task etl -- subject <应用> <系统> <一级菜单> <中文主题> --menu-path <一级菜单/二级菜单/...> --requirement <需求名> --menu-code <菜单编码> --menu-name <菜单名称>
task etl -- tree
```

`task etl -- subject` 会创建中心资产模板，并在需求目录 `04-产出物/ETL资产链接.md` 写入反向链接；已有文件不会被覆盖。

- `.rule/global/praxis-workflow/08b-轻量ETL调查与口径治理.md`：dbx 只读调查、口径卡、对账和落盘要求。

## 触发条件

出现以下任一场景，优先读取 `.skill/global/mom-lightweight-etl-report/SKILL.md` 和本规则：

- 报表、统计表、驾驶舱、积木报表、大屏报表数据。
- PostgreSQL 报表视图、函数、指标汇总、API 契约。
- MagicAPI 报表分页、查询、导出、调试、对账、口径说明。
- 字段来源、表关系、真实数据、指标口径、状态/单位/时间口径。
- 报表口径争议、数据对不上、口径版本变更和影响分析。

## 架构分层

## 系统与模块划分

报表/ETL 建模必须先明确系统和模块归属，优先按菜单划分，而不是按临时需求名、接口名或单个页面名划分。

模块划分顺序：

1. 通过数据库菜单表、前端路由、MagicAPI 分组或现有菜单授权确认系统和一级/二级菜单。
2. 优先使用菜单 `name/path` 作为目录层级，菜单 `code/component` 写入 README 和口径卡作为证据。
3. 若一个指标跨多个菜单，选择业务主责菜单作为主目录，在 README 中记录下游引用菜单。
4. 若菜单缺失或尚未确认，临时归入 `unclassified`，并在口径卡中标注“菜单归属待确认”。

MES 当前优先按菜单路径沉淀，示例：

```text
docs/03-etl/生产制造/MES/04-工厂建模/06-班次信息/
docs/03-etl/生产制造/MES/04-工厂建模/08-生产日历/
docs/03-etl/生产制造/MES/18-生产报工/02-挤压报工/
docs/03-etl/生产制造/MES/24-生产报表/01-投入产出/03-挤压产出汇总/
docs/03-etl/生产制造/MES/08-交班管理/04-交班记录/
docs/03-etl/生产制造/MES/10-工模管理/01-模具管理/
```

中心 ETL 资产目录建议结构：

```text
docs/03-etl/<应用>/<系统>/<一级菜单>/<二级菜单>/.../<中文主题>/
  README.md
  指标口径卡.md
  ETL.sql
  对账说明.md
  MagicAPI契约.md
  积木报表契约.md
  验证SQL.sql
```

`docs/03-etl/<应用>/<系统>/00-系统业务建模/` 用于沉淀菜单模块划分、表对象推断、菜单证据和跨模块引用规则。

创建或补齐该结构时，优先执行：

```bash
task etl -- init
```

### 元数据调查层

职责：

- 找出真实表、字段、主键、索引、注释、数据量级、时间字段、状态字段、单位字段和候选关联。
- 结合系统页面、接口返回、业务单据和现场口径确认业务含义。
- 输出证据、候选项和待确认问题，不把猜测写成确定结论。

### `rpt_base_*` 基础标准化层

职责：

- 对源系统对象做只读封装。
- 统一字段命名、时间、状态、单位、数值和通用标记。
- 保留源系统主键、源系统标识、创建/更新时间等溯源字段。
- 不计算复杂业务指标。

开发库第一版基础视图优先从 `references/base-and-rule-modeling.sql` 起步，已覆盖：

- MES 生产报工事件、任务单、任务工序。
- WMS 即时库存、库存流水、容器操作。
- QMS 过程检验。
- TPM 设备点检任务、设备主数据。
- MDM 物料主数据。
- data 设备数采指标。

### `rpt_rule_*` 公共规则函数层

职责：

- 沉淀跨报表复用的参数、时间、状态、单位、指标、权限和版本规则。
- 避免每个视图、MagicAPI 或积木报表重复写公共口径。
- 函数必须有 `COMMENT ON FUNCTION`，并说明用途、输入、输出、版本、适用范围和限制。
- 修改返回类型通常会影响依赖对象，设计前先确认签名稳定性。
- 公共函数需要补充通用过滤条件、显示字段或排序序号时，优先兼容增强既有公共函数，不为每个字段组合新增 wrapper 函数。
- 公共函数签名或返回类型变化必须提供幂等迁移语法、旧函数 `drop` 策略、旧调用兼容说明和依赖排查清单；默认不使用 `cascade` 掩盖依赖迁移问题。
- 多个函数复用同一字段集合时，优先沉淀组合类型、视图或稳定公共函数作为字段契约，减少重复 `returns table` 列表和重复 `select` 字段维护；最终 API 可保留平铺字段以兼容报表调用。
- 公共规则/事实函数不得带单一报表或单一需求名称；带报表名称的函数只能作为该报表专用入口或适配层，不能在资产索引中标记为公共可复用资产。

开发库第一版公共规则函数优先从 `references/base-and-rule-modeling.sql` 起步，已覆盖：

- 布尔标志位归一。
- 业务日期归属。
- 空数值归零。
- 安全比例。
- 库存方向符号。
- 任务、工序、质量结果、设备执行状态粗粒度归一。
- 日期范围校验。
- 指标版本号生成。

### `rpt_biz_*` 业务口径层

职责：

- 把基础标准化视图组合成业务事实。
- 固化业务日期、班次、状态、责任归属、计入/排除规则。
- 保留对账所需源对象引用。
- 不直接服务复杂页面展示。

### `rpt_metric_*` 指标汇总层

职责：

- 固化指标粒度、指标公式、过滤条件和指标版本。
- 支持多报表复用。
- 每个指标必须回答：按什么粒度算、按什么时间算、哪些数据计入、公式是什么。

### `rpt_api_*` API 契约层

职责：

- 给 MagicAPI 提供稳定查询入口。
- 输出前端友好的字段命名。
- 不暴露源系统复杂结构。
- 返回或可查询指标版本、口径说明和对账入口。
- 无参数或低风险查询可用视图；强参数查询优先用 `p_context jsonb` 或明确参数函数。
- 大数据量、时间敏感、按生产日期或业务日期查询的 API 契约禁止设计成无参全量视图；必须使用 `fn_rpt_api_*` 参数化函数，并把日期、租户、组织等参数下推到源表查询分支。禁止先读取全量业务口径视图后再在函数外层过滤。

### `rpt_debug_*` 和 `rpt_doc_*`

职责：

- `rpt_debug_*` 用于样例对账、明细追溯、差异排查，不开放给普通业务用户。
- `rpt_doc_*` 用于指标口径、接口契约、版本和适用范围说明。

## 命名规范

本项目默认不新增 schema，统一使用 `public` schema，并用对象名前缀表达层级：

```text
v_rpt_base_<主题>
fn_rpt_rule_<规则>
v_rpt_biz_<主题>
v_rpt_metric_<主题>
v_rpt_api_<主题>
fn_rpt_api_<查询>
v_rpt_debug_<主题>
fn_rpt_debug_<对账>
v_rpt_doc_<主题>
```

禁止：

- 用真实业务表名作为最终报表视图名。
- 用页面名直接作为业务口径层视图名。
- 一个视图同时承担清洗、口径、聚合、展示四种职责。
- 在 MagicAPI 或积木报表中重复实现公共口径。

## 数据调查

涉及表关系、字段来源、真实数据、报表口径、SQL、迁移或接口数据口径时，必须遵守 `.rule/global/praxis-workflow/03-调查门禁.md`。

优先调查：

1. 数据库 schema、表、视图、字段、注释。
2. 主键、唯一约束、索引、外键或隐含关联。
3. 数据量级、时间字段分布、状态字段枚举、单位字段。
4. 系统页面、接口返回、业务单据流转样例。
5. 业务方确认记录和对账样例。

元数据 SQL 只能作为调查模板，不能替代业务确认。无法连接数据库时，输出“未连接数据库，待人工确认”，不得写成已确认结论。

开发库基础调查已沉淀在 `references/dev-db-base-rule-modeling.md`，后续报表需求可以复用其中的对象候选，但仍需按具体报表主题确认字段含义和口径。

## 口径治理

三个强制原则：

```text
一指标一卡
一接口一注释
一报表一对账入口
```

指标口径卡至少包含：

- 指标编码、指标名称、所属主题、指标版本、当前状态。
- 业务含义、统计粒度、时间口径、计入规则、排除规则。
- 状态口径、单位口径、计算公式。
- 数据来源、上游视图、下游接口/报表。
- 对账样例、确认人、维护人、修改记录。

口径状态建议：

```text
CHECKING -> BIZ_REVIEW -> CONFIRMED -> CHANGED -> DEPRECATED
```

口径变更必须分析受影响的函数、视图、MagicAPI、积木报表、导出和验收样例，必要时升级指标版本。

## PostgreSQL 设计要求

- 复杂公共规则必须抽成函数。
- 每个视图必须有 `COMMENT ON VIEW`。
- 关键输出列必须有 `COMMENT ON COLUMN`。
- 每个函数必须有 `COMMENT ON FUNCTION`。
- 视图保留源对象溯源字段，便于 debug 对账。
- 不允许正式报表直接查询源表；debug 接口例外但必须说明原因。
- 不允许无限嵌套视图；性能敏感场景要评估过滤条件、聚合粒度、索引和物化替代方案。

视图注释应说明：

- 对象类型、对象名称、所属层级、所属主题、口径版本、状态。
- 业务用途、数据粒度、上游依赖、下游使用。
- 时间口径、计入口径、排除口径、单位口径、状态口径。
- 对账方式、维护人、更新时间、限制说明。

## MagicAPI 设计要求

MagicAPI 只承担接口编排：

- 接收参数、校验参数。
- 统一分页、排序白名单、安全动态条件。
- 调用 PostgreSQL API 契约视图或函数。
- 统一返回结构。
- 暴露调试/对账/口径说明接口。

要求：

- 必填参数使用 `assert` 或 `exit` 校验。
- 列表接口必须分页，优先使用 `db.page`。
- 普通查询参数使用 `#{}`。
- `${}` 只能用于白名单后的排序字段或排序方向。
- 动态 SQL 条件必须保持可审计，不拼接未经白名单处理的用户输入。
- 接口头部必须写数据契约、业务口径、参数、对账入口和修改记录。
- 不在 MagicAPI 中重复实现 PostgreSQL 已有公共口径。

### MagicAPI SQL 兼容门禁

PostgreSQL 能执行不代表 MagicAPI 能解析。报表脚本进入 MagicAPI 前必须按以下兼容门禁自查：

- 优先调用 `v_rpt_api_*` 视图或 `fn_rpt_api_*` 函数，不在 MagicAPI 里承载复杂业务口径 SQL。
- 涉及大表、历史明细或日期范围的报表，优先调用 `fn_rpt_api_*` 参数化函数；禁止 MagicAPI 或积木报表先读取无参 API 视图全量数据后再过滤。
- 禁止使用 `AS (WITH ... SELECT ...)` 这类 CTE 内嵌套 CTE。
- 复杂 CTE 链中尽量避免 `ROW_NUMBER`、`LEAD`、`LAG` 等窗口函数；必须使用时优先沉淀到 PostgreSQL 视图/函数层。
- 最终结果必须保留 `tenant_id` 等 MagicAPI 可能自动追加过滤的字段；聚合查询新增这类字段时必须同步补齐 `GROUP BY`。
- 避免 `SELECT *` 后依赖外层包装追加条件；最终 `SELECT` 字段应显式列出。
- 避免在 MagicAPI SQL 中写 `${startTime} - INTERVAL ...`、`${endTime} + INTERVAL ...` 等变量参与方言表达式；日期扩展窗口优先在 PostgreSQL 视图/函数中处理。
- 避免把 PostgreSQL 方言特性、复杂 `UNION`、窗口函数和动态参数混在同一个 MagicAPI SQL 中；无法避免时必须提供“MagicAPI 降级版”。
- 报错为 `PreparedStatementCallback; bad SQL grammar` 且信息不足时，优先怀疑 MagicAPI/JSQLParser 或自动租户包装，不先怀疑 PostgreSQL 语法本身。

### 快速修复版与 ETL 沉淀版

报表口径修复可分两层交付：

- 快速修复版：以 MagicAPI 兼容 SQL 或脚本快速恢复页面/接口，要求 SQL 保守、可调试、字段契约不变。
- ETL 沉淀版：把稳定口径设计为 `v_rpt_biz_*`、`v_rpt_metric_*`、`v_rpt_api_*` 或 `fn_rpt_api_*`，同时提供 `v_rpt_debug_*` 对账入口和口径卡。

若用户明确“本次 ETL 不一定落数据库”，仍应在需求目录沉淀 ETL 资产：

- `04-产出物/口径卡/`：指标口径卡。
- `04-产出物/SQL/`：ETL 视图/函数 SQL、COMMENT 注释和验收 SQL。
- `04-产出物/关联信息调查/`：源字段、样例数据、已确认/待确认口径。
- `04-产出物/MAGIC-API脚本/`：快速修复版脚本与薄接口版建议；老需求已有 `MAGIC-API脚本草案/` 时可沿用历史目录。

建议分组：

```text
/report/<subject>/page
/report/<subject>/summary
/report/<subject>/chart
/report/<subject>/export
/query/<subject>/detail
/debug/<subject>/raw
/debug/<subject>/compare
/doc/metric/detail
```

## 积木报表设计要求

积木报表只负责展示。推荐接入方式：

- 简单、稳定、低风险查询：SQL 数据集查询 `rpt_api_*`。
- 复杂参数、权限过滤、分页、动态排序、口径版本和对账入口：API 数据集调用 MagicAPI。

要求：

- 核心指标口径不放在报表表达式里。
- 报表说明中标识数据来源、接口或视图、指标版本和对账入口。
- 导出、打印和图表展示必须复用同一数据口径。
- 验收必须基于样例单据或 debug 明细。

命名建议：

```text
JR_<主题>_<用途>_<版本>
```

## 产出物

完整报表需求至少在需求目录沉淀：

- `01-需求分析拆解/`：业务主题、统计对象、指标、查询条件、待确认项、证据。
- `04-产出物/关联信息调查/`：元数据、表关系、字段候选、状态/单位/时间候选。
- `04-产出物/口径卡/`：指标口径卡。
- `04-产出物/SQL/`：PostgreSQL 视图/函数 SQL、COMMENT 注释、验收 SQL、菜单授权 SQL。
- `04-产出物/MAGIC-API脚本/`：MagicAPI `.ms` 和接口设计说明；老需求已有 `MAGIC-API脚本草案/` 时可沿用历史目录。
- `04-产出物/积木报表说明/`：数据集、参数、区域、导出、对账和验收说明。

正式 Flyway 目录只允许在收尾确认后写入，且必须能从 `04-产出物/SQL/` 找到来源。

若需求需要轻量 ETL 基础层：

- 先从 `references/base-and-rule-modeling.sql` 复制相关 `public.fn_rpt_rule_*` 函数和 `public.v_rpt_base_*` 视图到需求目录 `04-产出物/SQL/`。
- 删除本次需求不涉及的视图，避免一次性引入无用对象。
- 根据真实报表口径新增 `public.v_rpt_biz_*`、`public.v_rpt_metric_*`、`public.v_rpt_api_*`、`public.v_rpt_debug_*`、`public.v_rpt_doc_*`。
- 中间产物确认前不得直接写正式 Flyway。

## 验收清单

- 参数边界测试。
- 总数对账。
- 明细抽样对账。
- 异常状态测试。
- 空数据测试。
- 权限范围测试。
- 分页测试。
- 排序测试。
- 导出测试。
- 积木报表展示测试。
- 指标版本和口径说明可查询。
- 性能风险说明已落盘，必要时有 SQL 验证或 explain 思路。

## 常见排查分类

报表数据不一致时，先分类再改动：

- 源数据问题。
- 口径理解问题。
- 视图逻辑问题。
- MagicAPI 参数问题。
- 积木报表展示问题。
- 缓存、权限或分页问题。
- 业务方期望变更。

排查顺序：

1. 固定报表参数和样例单据。
2. 查 API 返回。
3. 查 debug 明细。
4. 对照指标口径卡。
5. 定位差异点和影响范围。
6. 判断是否需要升级指标版本。
7. 输出回归测试样例。
