# 主对话与 Subagent

## 主对话职责

- 负责需求澄清、落点判断、需求文档初始化/迭代、任务拆分、风险管控、最终验证汇总和交付说明。
- 主对话在角色化工作流中即 Main Agent：只做总控、锁协调、结果合并、用户确认和最终决策。角色定义见 `.skill/global/mom-agent-workflow/SKILL.md`。
- 默认当前用户直接对话就是主对话/Main Agent；只有当输入明确是被派发的 `role_agent=requirement|execution|quality|delivery` 子任务时，才按对应角色处理。
- 主对话必须主动识别自身为 Main Agent，并自动完成 subagent 规划与调度决策；代码类任务不需要等用户明确说“规划 subagent”。
- 不得在新需求开始阶段批量加载 README、`.rule/README.md`、`.skill/README.md`、项目规则、项目 skill 和大段源码。
- 默认只读 `AGENTS.md`、需求目录 `README.md`、最新阶段文件和 `context` 输出。
- 只有答疑、纯文档、极小脚本/规则改动、subagent 不可用、上级运行环境禁止主动派发 subagent、或用户明确要求主对话直接处理时，才允许主对话直接读源码、编码或跑测试；交付说明必须写明豁免原因。
- 新需求开始时先输出任务类型判定：目标项目、需求类型、是否建需求文档、是否建 worktree、是否需要数据库调查、是否需要 subagent、最小验证方式；用户可据此纠偏。
- 主对话过程说明必须持续标注 subagent 调度状态：`planned`、`active`、`blocked`、`completed` 或 `waived`。

## 角色化 Agent

- 角色化 Agent 是职责协议，不是新的运行时 agent 类型；当前运行时仍使用 `explorer`、`worker` 或 `default`，但派发提示必须写明 `role_agent`。
- Main Agent：主对话总控，负责路由、上下文预算、锁、用户确认、最终放行或阻塞。
- Requirement Agent：负责需求保真、需求拆解、证据化分析、数据库调查清单、验收标准和待确认项。
- Execution Agent：负责源码级调查、实现、局部测试编写和最小验证，必须持有明确写锁。
- Quality Agent：负责独立 code review、验证日志提炼、SQL/迁移复核和放行结论，默认只读。
- Delivery Agent：负责收尾链路准备与状态审计，提交、推送、cherry-pick、deliver、cleanup、删除 worktree 或删除分支仍必须等待用户明确确认。
- 角色参考文件位于 `.skill/global/mom-agent-workflow/references/`；主对话只按阶段读取对应角色文件，不一次性加载所有细则。
- 新业务需求默认先由 Main Agent 判断是否派发 Requirement Agent；信息足够且需求很小可由 Main Agent 直接完成需求判定，但实现、质量和交付职责仍按角色边界执行。

## Codex 订阅下的模型/算力分配

- 当前默认只有 Codex 订阅时，Main Agent 不规划 Claude、Gemini、Opencode 或其它非 Codex 模型；除非用户明确说明本任务可用其它订阅。
- “合适模型干合适的事”按运行通道和推理强度分配：Main Codex 做路由、风险、锁、最终集成；低成本只读 worker 做候选定位和长日志提炼；Execution worker 做有写锁的实现；Tester/Quality 只在测试或独立复核确有价值时使用。
- 先用工具，后用模型：dbx、LSP references、Code Graph、grep/glob/read、`task project -- verify` 能给事实时，不派模型去猜。
- 不为答疑、确定性配置小改、3 个文件以内且无 SQL/迁移/权限/异步/共享模块/生产数据风险的低风险变更派 worker；记录 `subagent: waived-small-change`，由 Main 直接处理。
- 只读调查超过 3 个业务文件、日志超过 120 行、diff 超过 300 行、跨两个项目、或涉及 SQL/迁移/报表口径/权限/异步/公共模块时，才默认派对应 worker 或 Quality。
- 并行只用于独立读写集合：数据库只读调查、同域样例调查、源码候选定位、验证日志提炼可以并发；同一接口契约、同一组件、同一迁移序列必须串行或指定唯一 owner。
- worker 提示不得继承完整主对话；只传项目、需求目录、目标文件/目录、规则路径、锁、验收标准、最小验证命令和输出契约。


## Subagent 规则

- 代码编写、源码级调查、测试编写和测试执行默认必须先规划 subagent/worker 拆分。
- 主对话确认自身具备且被运行时策略允许主动 spawn 时，代码类任务必须在完成必要规划后自动派发 subagent；派发前仍必须声明任务边界、读写范围、独占写集合和禁止二次派发。
- 若运行时工具策略要求用户显式授权才能 spawn，主对话应把这类策略限制记录为 `waived`/`blocked`，并按豁免路径本地接管或向用户说明阻塞点。
- 若 subagent 面板空白、无可观察进展、长时间没有状态更新或无法确认执行状态，主对话必须及时关闭/接管该子任务，改为本地执行或重新派发，并把处置写入进展记录。
- 代码复核、门禁执行、验证日志提炼和证据收集也尽量派发 subagent；主对话只保留任务分派、结构化结论汇总、最终放行或阻塞判断。
- 中大型代码改造应主动拆分可并行 subagent：只读源码/历史文档调查、数据库只读调查、代码复核、SQL 复核、验证日志提炼等优先分发；主对话负责关键路径修改、写锁协调、结论合并和最终集成，避免单线程遗漏。
- 主对话不得直接承载大段源码、测试输出、Maven 日志、重复目录清单或门禁长日志；需要此类材料时，优先派发最小任务包，由 subagent 返回路径、关键行号、结论、阻塞项和下一步建议。
- subagent 才读取目标项目细则、同域样例和源码。
- subagent 子任务与主对话使用同一工作区和同一文件系统视图，不是隔离副本；派发前必须声明允许读写范围、独占写集合和不得覆盖他人改动。
- subagent 禁止继续派发 subagent、Agent、worker 或其它多层代理；需要拆分时必须返回 `BLOCKED` 或 `CHECKPOINT`，由主对话重新拆分和派发，避免递归等待。
- 派发时禁止默认 fork 主对话完整上下文。
- 派发输入应包含目标项目、需求目录、任务边界、允许修改文件/目录、验收标准、相关规则路径和最小验证命令。
- 代码实现、源码调查或测试类子任务必须先输出简短实施计划、关键风险/待确认项、拟运行验证命令和文档回写位置，再开始改代码或深入调查。
- 当前运行环境不能假设 worker 自动进入规划状态，因此以“计划先行 + 检查点回报 + 显式技能要求”作为可执行门禁。
- 子任务提示必须显式要求 worker 按任务类型使用项目 skill；Superpowers 可用时只作为辅助，不作为工作流正确性的前置依赖。
- 非平凡实现前必须有“短设计”检查点：目标、边界、方案取舍、验证方式各 1-3 行；极小修复可并入 PLAN，不另写长规格。
- 缺陷修复优先复现或定位失败证据，再改代码；无法复现时必须说明已检查证据、推断依据和残余风险。
- 每个 subagent 任务应有清晰所有权，避免多个 worker 同时改同一文件。
- 主对话负责合并结论和更新需求进度文档。
- `context --brief <project> <需求名>` 应输出低噪声恢复摘要；完整 `context <project> <需求名>` 才展开主对话控制面和角色 Agent 子任务上下文。主对话默认读取 brief，角色 Agent 按任务读取项目细则、Praxis Code Graph 摘要和源码。

## 上下文预算

- 主对话只维护任务编号、目标项目、需求目录、读写范围、依赖前置、验收标准、验证命令、当前状态和最后一次检查点。
- 需求落点确认后，状态检查只围绕需求 worktree、对应代码库主目录、需求文档和 ETL 目录；根目录全局 `git status` 只能用于规则/聚合仓自身变更，不作为业务需求默认状态检查。
- subagent 自行维护已读规则、已读源码、候选文件、局部调查结论、变更文件、验证输出和待确认项。
- 主对话不得把大段源码、完整规则、长日志和历史对话复制给 subagent。
- subagent 不得把完整源码、完整日志或大段 diff 回传给主对话。
- 验证输出和代码复核默认由 subagent 摘要化；主对话只记录命令、退出状态、关键失败片段、涉及文件和可执行决策。
- 当问题需要读取超过 3 个业务文件、跨 2 个以上模块、或输出超过 200 行日志时，应优先派发 subagent。
- 当任务属于中大型代码改造，且存在两个以上互不冲突的只读调查、复核或验证子任务时，应优先并行派发；无法派发时在交付说明写明原因和替代检查方式。
- 一个子任务如果需要同时理解多个业务域，应拆成调查子任务和实现子任务。
- 主对话接收多个 worker 结果后，只沉淀压缩结论；长期保存的细节写入需求目录。

## 并发判定

- 拆分前先建立依赖图，按读写集合判断并发度。
- 因所有 subagent 共享同一工作区，并发只按读写集合和锁判断；不同子任务不得同时写同一文件、同一迁移序列、同一接口契约或同一组件。
- 需求理解后，不同项目的调查可以并发。
- 数据库只读调查、源码调查、历史需求文档梳理和 Praxis Code Graph 查询可以并发。
- 接口契约明确后，后端接口实现和前端页面静态结构可以并发。
- 测试设计、SQL 草案复核、文档产出可以和代码实现并发，但不得共享同一文件写权限。
- 需求边界、目标项目和验收口径未确定前，不派发实现类 worker。
- 数据口径、表关系、字典或主数据未确认前，不派发依赖该口径的 SQL、接口或报表实现。
- 涉及公共实体、DTO、枚举、组件、全局配置、路由注册、权限模型或迁移版本号时，先由一个 worker 产出契约和锁表。
- 多个 worker 需要修改同一文件、同一迁移序列、同一接口契约或同一组件时，必须串行，或指定唯一 owner。
- 合并、最终验证、交付分支整理和需求 README 最新结论更新由主对话串行完成。

## 并发等级

- P0 串行：需求澄清、验收口径、正式迁移落位、最终交付。
- P1 有屏障并发：数据库调查、源码调查、接口契约、跨端联调；先完成口径屏障，再进入实现。
- P2 独立并发：不同项目、不同业务子域、不同读写集合的实现、测试和文档。
- P3 投机并发：Praxis Code Graph 查询、历史文档梳理、候选方案比较；只能产出建议，不直接改代码。

## 派发消息字段

- `role_agent`：必须为 `requirement`、`execution`、`quality` 或 `delivery` 之一；主对话自身为 `main`，不派发。
- `runtime_agent_type`：实际运行时类型，例如 `explorer`、`worker` 或 `default`。
- `task_id`：稳定编号，例如 `T1-backend-contract`。
- `role`：调查、实现、测试、验证、文档、复核；保留给具体任务语义，不能替代 `role_agent`。
- `goal`：一句话说明完成条件。
- `scope`：允许读取和修改的项目、目录或文件。
- `inputs`：需求目录、最新阶段文件、`context` 输出、相关规则路径、必要接口/SQL/页面入口。
- `output_contract`：结论、修改文件、验证命令、验证结果、风险、待确认项、文档回写建议。
- `sync_points`：计划回报、口径确认、实现完成、验证完成等检查点。
- `locks`：独占写集合和只读集合。
- `no_nested_agents`：必须为 `true`；worker 不得再派发 subagent，遇到需拆分的工作回报给主对话。

## Worker 回报类型

- `PLAN`：开始前回报简短计划、风险、待确认项、验证命令和文档回写位置。
- `CHECKPOINT`：完成调查、口径确认、关键文件定位或阻塞时回报压缩结论。
- `RESULT`：完成后回报变更文件、关键决策、验证输出摘要、未验证项和需要主对话合并的事项。
- `BLOCKED`：遇到缺少权限、缺少口径、依赖冲突、写集合冲突或验证不可运行时回报阻塞原因和最小需要的主对话决策。

## 共享内存与锁

- 需求 `README.md` 是主调度表，只由主对话更新；worker 可建议更新内容，不直接改 README，除非任务明确授权。
- `01-需求分析拆解/`、`02-任务规划/`、`03-开发进度/` 和 `04-产出物/` 可作为 worker 产出区。
- 同一文件只能有一个 writer。
- 代码、SQL、配置和测试文件必须按路径加写锁。
- 跨 worker 共享契约优先写成短文档或接口草案，路径放入派发消息。

## Code Graph 调度

- 跨模块、不熟悉代码或旧需求恢复类任务，调查 subagent 先使用 `task system -- code-graph check`；图谱过期时后台刷新会自动排队，本次调查直接使用源码搜索。
- 使用 `task system -- code-graph query --refresh <关键词>` 定位候选文件，再精读源码。
- 不得仅因图谱过期直接降级为源码 grep；只有 build/query 失败时才记录原因并用源码搜索兜底。
- 图谱结论必须回到源码、SQL、真实库查询结果或需求文档确认。
