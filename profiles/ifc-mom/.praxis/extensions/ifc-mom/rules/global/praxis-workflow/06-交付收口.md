# 交付收口

## 定位

实现完成后的交付闭环：统一执行、cherry-pick、feature 分支和 worktree/分支清理，确保可追溯与可复核。

## 推荐入口（最小链路）

```bash
task project -- start <project> <需求名> <用户原始需求原文>
task delivery -- status <project> <需求名>
task delivery -- finish <project> <需求名>
task gate -- ready <project> <需求名>
task delivery -- deliver <project> <需求名>
task delivery -- status <project> <需求名>
task delivery -- cleanup <project> <需求名>
```

标准动作顺序：`status -> finish -> review -> ready -> deliver -> status -> cleanup`。
`status` 是只读收口总览，用于集中查看需求目录、worktree、feature 分支和 ahead/behind，不替代 `ready` 或代码复核。

## P0（必须）

- 实现/修复、提交、交付与清理必须拆分步骤；未获用户明确确认前，禁止：`commit`、`push`、`cherry-pick`、`deliver`、`cleanup`、删除 worktree/分支。
- `commit-split`、`deliver` 和 `cleanup` 前必须展示目标、变更、验证证据和残余风险，并等待用户明确确认。
- 代码修复/实现本身不等于交付完成；交付动作需单独确认。
- `ready` 聚合执行 preflight 与 guard；guard 内部覆盖 docs/change/migration/path 检查。`change-check` 与 `migration-check` 保留为专项诊断命令。
- `change-check` 与 `deliver` 必须执行脚本化交付策略检查：生产提交消息为 `type(scope): subject` + 空行 + 编号明细；MES PAD BFF Controller 变更必须包含菜单授权 Flyway 迁移脚本。
- 正式交付提交必须来自显式确认清单，不得用“非 `test:` 提交”作为默认筛选规则。`finish` 生成 `.praxis/out/delivery/<project>/<需求名>/confirmed-commits.txt` 候选清单后，Main Agent 或 Delivery Agent 必须复核并确认最终提交哈希；`deliver` 只 cherry-pick 该清单中的未注释哈希。
- `test-support:`、`local-test-support:`、`test:`、临时验证、本地测试依赖、`src/test`、仅新增 Maven `test` scope 依赖的 `pom.xml` 提交默认是 local-only，不进入正式 feature；若确需交付，必须有用户逐项确认。
- `deliver` 创建 feature 并 cherry-pick 后必须立即执行正式 feature 污染检查；发现 `src/test`、test-only `pom.xml`、临时验证文件、本地专用文件或 local-only 提交时阻断后续 push。
- `commit-split` 必须前置校验可识别的 commitlint `scope-enum`，避免进入 git hook 后才发现 scope 非法。

建议确认话术（示例）：

```text
实现和本地验证已完成。是否确认进入收口阶段？
执行动作：quality review、ready、commit-split、deliver、cleanup。
不执行：自动 push、自动 merge 到 local/develop、把 test: 提交并入 feature（未获你单独授权时）。
```

## P1（重要）

### finish 与 feature 分支

- `start` 必须用 `defaultBranch` 创建需求 worktree，并携带原始需求文本。
- `finish` 先校验 `defaultBranch` 与 `upstreamBranch` 差异，给出 `origin/<upstreamBranch>` 到 `feature/<需求名>` 的 cherry-pick 命令。
- `finish` 同时输出并写入显式交付候选清单；该清单是 `deliver` 的唯一提交来源，注释行和标记为 `local-test-support` 的行默认排除。
- `finish` 还必须说明需求 worktree 基座与 `origin/<upstreamBranch>` 的差异：是否依赖 local 上未进入上游的历史提交，cherry-pick 到上游基线预计新增/修改哪些文件，历史修复、测试文件或大段上下文是必要依赖还是需要拆分重做。
- feature 分支必须从 `origin/<upstreamBranch>` 创建；不得从 `local` 直接切出。优先使用 `git switch --no-track -c feature/<需求名> origin/<upstreamBranch>`。
- 创建 feature 后立即执行 `git branch -vv --list feature/<需求名>`；若显示跟踪 `origin/<upstreamBranch>`，必须 `git branch --unset-upstream feature/<需求名>` 后再继续。
- `upstreamBranch` 统一以 `praxis.projects.toml` 为准；后端/Web=`develop`，PDA/前端分支按项目配置。
- `finish` 不默认 push、不默认 merge 回 local；不默认跑整体验证。

### 用户直接收尾

- 当用户明确说“直接收尾”时，停止新增需求文档、分析记录、README 索引等非代码产物。
- 只执行用户要求的收尾动作：提交、创建 feature、cherry-pick、验证、状态报告。
- 若已有文档或过程记录变更，不带入业务 feature；最终说明哪些内容未进入 feature。

### Cherry-pick 冲突

- cherry-pick 冲突时，不要机械接受 ours/theirs；先说明冲突原因：`origin/<upstreamBranch>` 缺少 local 前置修复、同文件并行修改，还是测试文件在上游基线不存在。
- 按用户要求确认保留范围：代码修复必须保留；用户要求带 spec 时，spec 必须保留；需求文档和本地配置不得进入 feature。
- 冲突解决后必须运行冲突标记扫描和目标测试；无法运行时说明原因和人工复核范围。

### 已提交 feature 验证

- 如果 `task project -- verify <project> <需求名>` 在已提交 feature 上返回 “No git changes found” 或等价空跑结果，不能把它当作充分验证。
- 改用 `origin/<upstreamBranch>...HEAD` 的变更清单执行替代验证：先运行 `git diff --name-only origin/<upstreamBranch>...HEAD`，再对变更文件执行 scoped eslint/test/compile。
- 交付说明必须报告 task verify 跳过原因和替代验证命令。

### Code review 要点

- 口径一致性、事务边界、异步/异常、幂等性、迁移与 SQL 幂等、测试覆盖范围。
- 生产修复类变更必须引用对应项目规则与验收证据。
- 最终 cherry-pick 清单逐个核对 `git show --stat`；发现 `pom.xml` test-scope 依赖、`src/test`、本地验证字样、临时脚本或 codex-only 文件时阻断或要求用户逐项确认。

### Feature 提交与迁移收口

- feature 提交按 `origin/<upstreamBranch>` 派生：`feature/<需求名>`。
- 临时验证和本地测试辅助提交（`test:`、`test-support:`、`local-test-support:`）默认不进入 feature。
- 迁移类收口要求：中间产物要有来源和差异复核记录；最终收口前先写明中间产物路径、正式路径、`migrationOwner=<project>` 与复核结论。

### cleanup

- `deliver` 成功后执行 `cleanup`，前置确认需求 worktree/feature 无未提交内容。
- 清理内容默认包含已登记的 `.worktrees/<project>/<YYYY-MM-DD-需求名>*` 和本地 `codex/*`，保留 `feature/*` 便于用户签出。

```bash
task delivery -- cleanup <project> <简短中文需求名>
```

## P2（持续优化）

- 交付/迁移收口模板继续收敛为同一结构化复用模板。
- 规范 `commit-split` 与 `feature` 拆分策略，降低多轮提交造成的 review 负担。
- 逐步把 cleanup 的清单化项（路径、分支、未提交项）标准化。

## 交付说明包含项

- 涉及项目与验收边界。
- 是否使用 worktree，若豁免要写明原因与风险。
- Web 场景需写可测试路径与同步配置。
- 修改文件清单。
- 需求基座与 `origin/<upstreamBranch>` 差异、隐含 local 依赖、预计 cherry-pick 文件清单。
- `task verify` 是否空跑及替代验证命令。
- 验证等级、执行命令、失败项与未验证项原因。
