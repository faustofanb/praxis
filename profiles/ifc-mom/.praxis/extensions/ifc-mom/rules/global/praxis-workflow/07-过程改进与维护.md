# 过程改进与维护

## todo.md 使用

- 根目录 `todo.md` 是后续所有任务持续维护的过程改进日志。
- `todo.md` 只记录用户在任务过程中指出的执行不规范、工作流缺口、以及后续应固化到规范或工作流的优化要求。
- `todo.md` 不记录普通任务计划、代码修改清单、临时代办或当前任务步骤。
- 规则维护、流程纠偏、环境配置、工具配置、脚本入口说明、插件/skill 配置、过程改进和 Codex 行为约束属于非业务需求，禁止为此创建或写入 `docs/02-req/YYYY-MM/` 需求文档；确需需求化跟踪时写入 `.praxis/requirements/`。
- 当 `todo.md` 中的要求稳定后，应同步更新到 `AGENTS.md`、`.praxis/extensions/ifc-mom/rules/` 或 `.praxis/extensions/ifc-mom/skills/`。
- 每个业务需求收尾时必须汇总本需求过程中出现的工作流优化项和代码质量优化项，分别写入 `todo.md` 对应分类；同时简要评估工作流执行效率和上下文空间利用率，能固化的规则应同步更新到 `.praxis/extensions/ifc-mom/rules/` 或 `.praxis/extensions/ifc-mom/skills/`。
- 每个业务需求进入最终收口时，必须新增一份 `03-开发进度/<序号>-<日期时间>-工作流效率与上下文利用率复盘.md`，并通过 `task req -- index` 回写 README；复盘至少包含 subagent 产物交付情况、主对话上下文消耗、收尾流程符合度、`todo.md` 或规则固化建议。

## 工作流优化路线图

### P0（必须）

- 根目录 Git 仓库只管理工作流文件，业务子项目、`docs/` 和 `.worktrees/` 由各自仓库或流程管理。
- 新需求开始前先输出任务类型判断，覆盖项目落点、需求类型、文档、worktree、数据库调查、subagent 与最小验证方式。
- 接手卡住或恢复中的需求时，必须先读需求 README/阶段文件并执行或说明无法执行 `context`/`preflight`，确认 worktree、文档和验证门禁后再继续。
- `00-原始需求/` 必须完整保留用户原始描述，长 SQL/脚本/接口示例/截图说明和附件留档状态不得以摘要替代。
- `task req -- init` 不允许明显占位原文；`task req -- check` 必须校验原始需求文件与附件/截图未落盘说明。
- 用户贴附件时必须保存到 `00-原始需求/附件/` 并建立相对链接；无法取得时记录“附件未落盘原因”和补传路径。
- subagent 与主对话共享工作区，派发时需声明读写范围和写锁；subagent 禁止继续派发 subagent，需回报主对话。
- 所有业务代码需求无论大小都必须创建需求 worktree 并在 worktree 中推进；不得以微小修复、单文件改动或文案很小作为豁免理由。
- 生产库或疑似生产数据不允许未确认直接查询；需先确认环境、范围、条件与风险，并获用户许可后执行，禁止全表扫描。

### P1（重要）

- 新增 `preflight` 自动汇总需求目录、worktree、最新阶段文件、是否涉库/SQL/迁移、推荐验证命令和文档索引问题。
- 新增 `praxis-profile` 自动校验Praxis 通用配置、项目适配配置、命令引用和可移植阶段。
- 新增或修改 `.praxis/extensions/ifc-mom/rules/`、`.praxis/extensions/ifc-mom/skills/`、`.praxis/templates/` 后运行 `task system -- template-check`；新增 rule 或 skill 优先使用 `task system -- template-render rule ...` 或 `task system -- template-render skill ...` 生成基础骨架。
- `task req -- check` 增强为必须校验：README 引用最新 analysis/plan/progress，且不得存在模板占位。
- analysis/plan/progress 模板默认包含：用户原始需求、当前结论、证据来源/决策、待验证项、下一步。
- 收口确认话术模板已固化：提交、deliver、cleanup、删除 worktree 或分支前需明确用户确认。
- Web worktree 创建后同步主工作区忽略但必须的 `.env*`，交付说明需列出可测试 worktree 与同步配置。
- Web/PDA 验证脚本发现 worktree 缺 pnpm 依赖时自动先执行 `pnpm install`，安装失败才判定阻塞。
- 业务需求验证按变更范围执行，不以全局校验作为默认门禁；前端/PDA eslint 禁止默认全仓扫描。
- 首次调查后必须新增 `01-需求分析拆解/` 证据文件；需求命名需明确业务对象，泛名需补充具体对象。
- 任务完成时优先用实质内容替换阶段文件和 README 的占位，并在最终回复前复核“最新结论/阶段索引”非占位。
- 中大型改造应并行派发独立的 subagent（调查、复核、SQL 复核、验证日志提炼），主对话承担写锁与关键路径整合。

### P2（持续优化）

- 数据库调查按强制 / 风险提示 / 可豁免分级：SQL、迁移、报表口径、数据修复、字段映射为强制场景；仅解释代码逻辑或仅低风险前端文案可豁免并记录原因。

## 规则维护

- 新增子项目时先更新 `praxis.projects.toml`。
- 新增或改名自动化脚本时同步更新本目录相关文件、`../06-Praxis任务执行规范.md` 和 `../README.md`。
- 若某类规则仅适用于单个项目或单类需求，不默认提升为全局规范。
- 入口文档只保留导航和少量硬门禁；细则放入本目录或项目规则。

## 当前拆分约定

- `../06-Praxis任务执行规范.md` 只做索引，不再承载长篇执行细则。
- `../00-工作流精简索引.md` 负责细粒度定位。
- 本目录文件负责可执行细则。
