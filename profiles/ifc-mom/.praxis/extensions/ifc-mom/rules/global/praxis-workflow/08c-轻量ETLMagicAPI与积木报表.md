# 轻量 ETL MagicAPI 与积木报表

## 定位

本文件约束报表数据从 PostgreSQL 分层对象进入 MagicAPI、积木报表和大屏展示的接口契约。PostgreSQL 能执行不代表 MagicAPI 能解析，必须提前做兼容性设计。

## MagicAPI 边界

- MagicAPI 只做参数校验、分页、排序白名单、权限过滤、返回结构和调试入口。
- 复杂公共口径必须下沉 PostgreSQL 视图或函数，禁止在 MagicAPI 中复制大段公共口径 SQL。
- 普通参数使用 `#{}`；`${}` 只允许用于白名单后的排序字段或方向。
- 最终查询必须显式输出租户、组织、权限过滤需要的字段，避免自动过滤包装后字段缺失。
- 禁止 `SELECT *` 作为最终契约。

## 兼容性禁区

- 避免 `AS (WITH ... SELECT ...)` 嵌套 CTE。
- 避免在复杂 CTE 链中直接使用多级窗口函数；需要时优先做 `v_rpt_api_*` 或 `fn_rpt_api_*`。
- 避免 `${param} - INTERVAL ...`、`${param}::date` 等 JSQLParser 兼容性差的参数方言。
- 遇到 `PreparedStatementCallback; bad SQL grammar` 且 PostgreSQL 原 SQL 能跑时，优先排查 JSQLParser、自动租户包装和外层字段缺失。

## 大数据量报表

- 大数据量、时间敏感、按生产日期或业务日期查询的 API 契约禁止设计成无参全量视图。
- 必须优先使用 `fn_rpt_api_*` 参数化函数，并把日期、租户、组织等参数下推到源表查询分支。
- 不允许先读取全量业务口径视图后再在函数外层过滤历史数据。

## 积木报表与大屏

- 积木报表只负责展示、导出、打印和少量展示表达式；核心指标不能放在报表表达式里计算。
- 需要导出、分页、排序、权限和口径版本时，优先由 MagicAPI 提供稳定数据契约。
- 大屏或高频刷新报表必须评估实时函数、普通视图、物化视图和汇总表方案，并写明刷新/补算策略。
