# 代码质量与注释规范

## 总要求

- 代码必须可读、可维护、可验证
- 注释不可缺失
- 注释应解释业务语义、边界条件和设计意图，而不是重复代码字面含义

## 注释要求

### 类、模块、文件

- 核心类、公共模块、重要文件必须有清晰注释
- 注释要说明职责、适用范围和关键约束

### 方法、函数、接口

- 对外方法、关键业务函数、接口定义应有说明
- 需说明输入输出、关键副作用或前置条件
- Python 自动化脚本优先为关键函数补方法级 docstring，说明方法职责、输入语义和关键流程原因
- TypeScript 自动化脚本应为关键导出函数、复杂范围识别和命令编排逻辑补充中文说明

### 字段与类型

- 关键字段、业务状态字段、核心 VO/DTO/Entity/Model 字段应有清晰业务含义说明
- 易混淆字段必须明确单位、状态语义或取值范围

### 复杂逻辑

- 复杂业务判断、性能优化分支、异常路径、兼容性处理必须有行内注释或块注释
- 自动化脚本中的配置读取、Git/worktree 分支判断、文档初始化幂等保护、上下文输出、交付收口和验证等级选择属于关键逻辑，必须在代码附近补充必要中文注释
- 注释使用中文，便于团队协作

## 代码质量要求

- 遵循 DRY、KISS、YAGNI
- 输入要校验，异常要可解释，日志要可追踪
- 删除无用导入、无用变量和无意义占位代码
- 不提交“临时可跑但结构明显失衡”的实现
- 自动化入口文件不得长期承载过多职责；应按配置、路径、文档、Git/worktree、上下文、验证、交付收口等职责拆分模块
- 不为单一调用点、单一 Job 或单一页面的局部逻辑过早抽象独立服务；只有复用、事务边界、复杂业务编排或同域既有模式明确需要时才新增抽象层。
- 配置类迁移脚本不得使用业务无关固定 ID、`max(id) + 1` 或手写 ID 生成逻辑；应优先依赖数据库默认主键生成或已有生成函数，并按业务唯一键保持幂等。

## 日志与异常

- 业务异常要清晰明确
- 日志使用统一日志体系，不输出敏感信息
- 禁止使用 `System.out.println` 或等价调试输出作为正式代码
