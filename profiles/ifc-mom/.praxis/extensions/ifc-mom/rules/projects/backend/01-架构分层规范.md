# 架构分层规范

## 项目架构概述

`ifc-mom-column-max` 采用 lamp 风格分层架构。

典型结构：

```text
lamp-{module}/
├── lamp-{module}-entity/
├── lamp-{module}-biz/
├── lamp-{module}-controller/
├── lamp-{module}-facade/
└── pom.xml
```

## 分层职责

### Entity 层

- 定义 Entity、VO、DTO、Query
- 与数据库、输入输出模型保持清晰边界

### Biz 层

- Service：业务编排和事务
- Manager：单表能力和可复用数据访问能力
- Mapper：数据库访问

### Controller 层

- 处理请求、参数校验和轻量逻辑
- 不下沉业务编排和数据库操作

### Facade 层

- 用于跨服务、跨模块调用
- 在单体和微服务两种启动方式间提供统一抽象

## 约束

- 严禁把业务逻辑堆到 Controller 或 Mapper
- Manager 只负责单表能力和通用能力下沉
- Service 承担完整业务流程和事务边界
- 定时任务类需求如果业务逻辑只服务单个 Job，默认不为形式上的分层单独拆 Service；可以内聚在 Job 类中，保证调度入口、数据窗口、主数据定位、状态判断和预警发送条件清晰可读。
- 当定时任务逻辑需要被多个入口复用、涉及明确事务边界、或已形成独立业务流程时，再下沉到 Service，并保持 Controller/Job -> Service -> Manager -> Mapper 的职责边界。
- 新增消息类 Job 设计幂等键、批次号或业务关联键时，必须先确认落库字段长度、唯一索引和重复写入策略；例如 `base_msg_task.biz_id` 为 `VARCHAR(100)`，不得直接拼接业务类型、长文本值和时间导致入库失败。
