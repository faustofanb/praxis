# 数据库迁移与 Flyway 规范

## 基本约束

- 数据库表迁移使用 Flyway
- 迁移相关需求必须先在需求目录沉淀中间产物，作为正式确认前的唯一参考来源；新 v2 需求统一放入 `04-产出物/SQL/`，老需求已有 `中间文档/` 时可沿用既有目录
- 开发和调查阶段禁止直接改写正式 Flyway 迁移目录下的 SQL 文件，不因“先写了更方便”跳过中间产物
- 只有进入收尾环节，且中间产物已由用户或主对话确认、来源和差异已复核后，才允许把已确认 SQL 迁移到正式 Flyway 目录
- 用户负责最终生成迁移脚本时，助手只在需求目录中间产物中输出 SQL/脚本、拆分稿、差异检查、风险提示和结果复核，不直接改迁移目录
- 迁移脚本是否落盘、如何合并、是否执行，由用户最终决定；交付说明必须写清中间产物路径、正式迁移路径和复核结论
- 正式 Flyway 迁移脚本文件名中的时间必须取本机真实时间；不得使用计划时间、估算时间或手工占位时间规避版本冲突
- 跨项目需求必须在需求文档中声明正式迁移归属，例如 `migrationOwner=backend`；非 owner 项目看到 SQL 中间产物时只提示需随 owner 项目迁移一起交付，不要求本项目携带 Flyway。

## 设计步骤

1. 先查看同域已有表结构。
2. 对齐字段命名、主键、审计字段、状态字段和索引习惯。
3. 先在需求目录 `04-产出物/SQL/` 输出迁移 SQL、按对象拆分稿、模型设计、应用设计、接口设计、菜单授权、MagicAPI 迁移说明等中间产物；老需求已有 `中间文档/` 时可沿用既有目录。
4. 对跨项目需求记录 `migrationOwner=<project>`，并说明非 owner 项目的交付分支是否只包含页面/接口配套改动。
5. 基于中间产物完成源码、页面、接口或本地验证调整，并记录差异与待确认项。
6. 收尾环节确认中间产物后，才把已确认 SQL 迁移到正式 Flyway 目录，并检查路径、版本号、顺序和冲突。
7. 若用户要求“只出中间文档、不直接改迁移脚本”，则停留在需求目录中间产物和复核结果，不进入正式 Flyway 目录。

## SQL 风格

- Flyway SQL 保持简单直接
- 避免不必要的 DO 块和复杂兼容逻辑
- 需要幂等时，优先采用 `DROP TABLE IF EXISTS` 后再 `CREATE TABLE`
- 低代码生成的新建物理表 DDL，可在中间产物确认后按导出版本进入正式迁移；`DROP TABLE IF EXISTS` 是项目内用于重复执行和结构重建的常见幂等写法，不能仅因包含该语句就归类为破坏性迁移。

## 中间产物拆分

- 迁移产出物必须按类型拆分目录或文件：新表 DDL、视图 DDL、菜单/授权 SQL、配置数据 SQL、迁移总稿分别维护，便于逐类复核和复制。
- MagicAPI `.ms` 脚本放在需求目录 `04-产出物/MAGIC-API脚本/`，不混入 `04-产出物/SQL/` 的 `.sql` 文件；老需求已有 `MAGIC-API脚本草案/` 时可沿用历史目录。
- 用户只要求 MagicAPI `.ms` 脚本时，只输出 `.ms` 和接口说明；不得额外生成 `magic_api_file` 更新 SQL，除非用户明确要求迁移 `magic_api_file` 或完整 Flyway 迁移脚本。
- SQL 产出文件只保留 SQL、注释和必要执行说明；执行前检查、SQL-only 验证结论、风险复核等应单独放入 `.md` 说明文件，不混入 `.sql`。

## 配置类数据迁移

- 消息渠道、消息模板、字典、菜单授权、低代码配置等配置类 SQL 必须优先按业务唯一键幂等更新，不得依赖环境相关的固定主键。
- 新增配置类数据前，应先确认目标表主键是否存在数据库默认生成机制；有默认值时省略 `id` 字段，让数据库生成主键。
- 如果目标表没有主键默认值，应优先使用数据库已有生成函数，例如 `public.generate_snowflake_id()`；不得使用 `max(id) + 1`、手写雪花算法或业务无关固定 ID 规避冲突。
- 配置类 SQL 的中间产物必须写清业务唯一键、冲突处理方式、主键生成方式和是否需要目标库人工复核。
- 若低代码导出、菜单、接口、字典等配置 SQL 必须保留固定主键 ID，默认采用“按固定 ID/业务键先删后插”的幂等方式；不得只依赖 `not exists`，避免半执行、补充脚本重复执行或业务键判断不完整时触发主键冲突。
- 固定 ID 配置迁移必须写清删除范围，删除顺序按外键依赖先子后主；禁止使用宽泛条件误删同域其他配置。

## SnailJob 配置迁移

- SnailJob 定时任务表属于独立数据库时，不得写入业务后端 Flyway 迁移目录；需求目录可保留外部库配置参考，但必须明确目标数据库、执行主体和是否由用户或运维手工执行。
- SnailJob 配置脚本必须先按同域样例、真实表结构和表注释确认枚举含义，不能只凭字段名推断触发类型、执行器类型或路由策略。
- Job 类定时任务使用 cron 表达式时，配置脚本应使用 cron 触发类型；当前 SnailJob Job cron 场景 `trigger_type = 3`，不得误用固定时间、固定间隔等非 cron 触发类型。

## SQL-only 验证口径

- 仅修改 Flyway 迁移脚本、SQL、DDL、菜单 SQL 或视图 DDL 时，不默认执行 Java/Maven 编译验证
- 优先复核 SQL 内容是否符合业务语义、字段类型和索引约定
- 必须检查文件路径、命名、Flyway 版本号、执行顺序和是否与已有脚本冲突
- 交付说明中写清是否已做人工执行、目标数据库环境、未执行原因和建议执行方式

## 中间文档协作约定

- 新 v2 需求不再新建 `中间文档/` 目录；迁移中间产物统一放在 `04-产出物/SQL/`。老需求已有 `中间文档/` 时，为保持历史上下文可沿用既有目录
- 当用户明确要求“我来生成迁移脚本，你只负责 check”时，助手输出物应只放在对应需求目录下，优先参考已有需求中的“迁移文档整理”拆分方式
- 中间产物至少应覆盖：模型设计、应用设计、接口设计、菜单与授权说明、正式迁移前差异复核结论
- `magic-api` 脚本、页面查询字段、字段精度、资源路径、pageId 等关键输入必须写入中间文档，避免只存在于对话里
- 在用户未明确确认且任务未进入收尾前，助手不得把这些中间材料反向落到 Flyway 迁移脚本中
