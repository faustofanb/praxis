# 调查分析

## 1、需求目标

把 Praxis 工作树从“阶段/仓库目录驱动”改为“需求工作空间驱动”，并在调查节点加入
Grill Me 的真实执行技能 `grilling`，随后用 MOM、AOTU 的 backend 仓库验证完整链路。

## 2、业务背景

当前 Codex 展示为 `backend (需求名__REQ-ID)`，分支为
`req/REQ-ID/02-backend`。用户希望需求 ID 前置、仓库作为需求工作空间的关联项、开发
阶段共享一个分支，并保留创建后的验证工作树供人工检查。

## 3、当前实现

- `WorktreeService.create_for_requirement` 把分支固定为 `req/<REQ>/<阶段编号>-<阶段>`。
- 目录固定为 `.worktrees/<需求简称>__<REQ>/<阶段编号>-<阶段名>/<仓库ID>`。
- runtime_state 的 worktree 记录直接以分支名作为 key；同一需求在多个 Git 仓库使用同名
  分支时会相互覆盖。
- binding 的 `path` 同时承担“Codex 打开的需求工作空间”和“实际 Git worktree”两种含义，
  因而无法把仓库关联到统一需求根目录。
- 调查策略要求 `brainstorming` 与 `ponytail`，尚未包含 Grill Me。

## 4、涉及业务域

`plugin-development`。

## 5、涉及系统和仓库

Praxis V3 插件仓库；验收工作空间为 MOM 与 AOTU，各选择 `backend`。

## 6、涉及模块

- `src/praxis/worktree/service.py`
- `src/praxis/worktree/lifecycle.py`
- MCP/Agent 对 worktree binding 的解析
- `skills/praxis-system-development/references/node-routing.toml`
- Agent 指引与相关文档

## 7、业务规则

1. 需求工作空间根目录为 `.worktrees/<REQ-ID>__<固定简称>`，ID 前置。
2. 实际 Git worktree 位于需求根目录下的 `<REQ-ID>__<固定简称>__<repository_id>`，
   让 Fork 展示的末级目录也保留需求语义。
3. 同一需求所有开发阶段在每个仓库中统一使用 `praxis/<REQ-ID>__<固定简称>`。
4. worktree binding 使用稳定的 binding ID，并允许同一需求关联多个仓库；不能再用分支名
   作为全工作空间唯一键。
5. `path` 表示需求工作空间，`repository_path` 表示实际 Git worktree。
6. 调查节点必须完成 `grilling`；`grill-me` 只是禁用模型自动调用的用户入口，不能用它
   代替真实访谈凭证。

## 8、数据口径

工作树同步证据必须包含本地模板分支、上游远端分支、同步后 revision、仓库 ID、binding ID、
需求工作空间路径和实际仓库路径。

## 9、接口与数据流

需求 ready → 同步 `origin/<template_branch>` 到干净的 `default_branch` → 创建或复用
`praxis/<REQ-ID>__<固定简称>` → 把可读仓库 worktree 放入需求根目录 → 持久化 binding → 生命周期按
binding ID、分支和实际仓库路径解析绑定。

## 10、现有能力复用

复用 Worktrunk、自有 StateStore、已有本地模板同步流程和节点 Skill 路由，不增加依赖。

## 11、代码图谱调查

本轮用定向 `rg` 找到所有 worktree binding 的直接读写点；未运行 CodeGraph 初始化或质量
分析。

## 12、数据库调查

不涉及业务数据库。Praxis SQLite runtime_state 仅调整 key 和记录字段，不做 schema 迁移。

## 13、影响范围

工作树创建、删除、合并、生命周期钩子、Agent/MCP worktree 授权以及测试断言。

## 14、风险分析

- 兼容风险：已有记录以 branch 为 key，需要解析器兼容旧记录。
- 多仓库风险：同一分支名跨仓库合法，但全局状态不可再按 branch 唯一。
- 路径风险：安全门禁必须针对 `repository_path`，而 Agent 工作目录可使用需求根目录。
- 缓存风险：当前会话能力列表仍显示旧 Praxis 插件缓存，重装后只能由新任务加载。

## 15、待确认事项

暂无。用户已确认 MOM、AOTU 均使用 backend，创建后保留工作树；命名要求以本需求规则为准。

## 16、调查证据

- 当前实现：`src/praxis/worktree/service.py:183-260`。
- binding 消费点：worktree lifecycle、MCP broker、Agent service。
- Grill Me 来源：`mattpocock/skills` v1.1.0，MIT；已安装 `grill-me` 与 `grilling`。
- 当前调查已记录 praxis-requirement-workflow、brainstorming、ponytail、file-search、
  find-skills 的 invoked/completed 证据；`grilling` 等策略改造后补录真实证据。

## 17、分析结论

采用一个需求根目录关联多个仓库 Git worktree 的方案。它满足 Codex 以需求为中心展示，
同时保留 Git worktree 必须属于单一仓库的技术事实；相比平铺多个目录或限制单仓库需求，
该方案对现有多仓库需求兼容最好。

## 18、第三轮 CodeGraph 中断调查（2026-07-21）

- MOM 的首次真实初始化在调用端约 22 秒后失联，binding 停留在 `initializing`，当时
  `.codegraph/lock`、WAL 和 SHM 仍存在，数据库约 445 MB。
- 后续只读复查时数据库增长到 681,091,072 字节，lock/WAL/SHM 已消失；`lsof` 未发现占用。
- `codegraph status --json`（1.3.0）确认索引 `state=complete`、`pendingRefs=0`，包含 9,828
  个文件、318,185 个节点、419,560 条边，且工作树没有待同步变更。
- Praxis 没有 `codegraph.init` / `worktree.codegraph_initialized` 完成审计，binding 仍为
  `initializing`。这证明 CodeGraph 子进程在调用方失联后完成，但仅存在于 Python 进程内的
  收尾逻辑没有执行。
- 不能靠删除 `.codegraph` 或盲目重新 `init` 修复；需要持久化操作尝试和心跳，并在重入时
  校验、收养已完成索引。索引仍有 lock 或操作心跳新鲜时应保持 initializing/busy，不能
  错误标记 blocked 或并发执行 sync。

## 19、第四轮门禁绕过调查（2026-07-21）

- MOM `REQ-20260721-004` 与 AOTU `REQ-20260721-002` 都在没有 `ready` 节点 route/gate
  的情况下进入 `ready` 并创建 active 工作树；补跑 gate 均返回 `SKILL_ROUTE_NOT_FOUND`。
- `PraxisApplication._gate_current_skill_route` 在 route 不存在时直接返回成功，是状态流转
  fail-open 的根因；`SkillInvocationService.gate` 的同类早退又发生在审计之前。
- `worktree.create` 只检查需求状态，没有调用当前节点 Skill gate，因此即使状态历史已被旧版
  工作流污染，仍能继续创建工作树。
- 清理验证现场时，Worktrunk 返回 `branch_deleted=true`，但两个 Git 分支实际仍存在，需求根
  目录也为空残留；Praxis 当前直接信任外部结果，缺少后置核对。
- 设计比较：自动补 route 会把“路由计划”伪装成完成凭证；新增独立事务/收据层超出本轮需要；
  选择复用现有 gate 的 fail-closed 方案，所有失败都审计，状态流转和 worktree create 都显式
  阻断，删除后仅核对真实状态并报告不一致。
- 路由意图中的“状态迁移”还会因裸子串“迁移”误命中 DBX；本轮不调用无关数据库技能，列为
  P1 路由语义优化，不与 P0 门禁修复混合。

## 20、第五轮本地运行文件调查（2026-07-21）

- MOM 当前 Web 主仓库存在 `apps/web-antd/.env.development`，Git 明确将其忽略；需求工作树
  `REQ-20260721-003__汽车件简单时效MES_PDA/web` 中该文件不存在，因此工作树无法直接运行。
- AOTU Web 主仓库也存在并忽略相同路径。Git worktree 不复制 ignored 文件属于正常行为，
  但 Praxis 将 binding 标成 active 前没有环境准备阶段，是工作流完整性缺陷。
- ignored 文件不能从固定模板 worktree 获取，因为该模板本身也是 Git worktree；权威复制源
  应为 `project.path` 配置的主仓库目录，目标为需求仓库工作树中的同一相对路径。
- 设计比较：批量扫描 `.env*` 会扩散未声明的密钥；软链接让需求工作树依赖主仓库绝对路径；
  选择项目级 `local_files` 白名单复制，且目标已存在时不覆盖。
- 安全边界：配置只接受规范仓库相对路径；运行时再次检查源/目标 resolve 后仍在各自仓库内，
  源必须为文件，目标不得是目录或越界符号链接。失败时 binding 保持 blocked，CodeGraph 不启动。
- 本轮用户未明确批准执行测试或质量复核；只实施代码、配置和当前工作树补齐，测试执行保持
  `blocked_pending_approval`。

## 21、第六轮前端依赖准备调查（2026-07-21）

- Git worktree 不共享仓库内的 `node_modules`；pnpm 的内容寻址 store 可以复用包内容，但每个
  新工作树仍需生成自己的依赖链接和模块布局，手工执行 install 会破坏“创建后可运行”目标。
- MOM/AOTU 的 Web、各 UniApp 与大屏仓库均存在 `pnpm-lock.yaml`；仅 Web 需要先复制
  `.env.development`，但所有这些前端工作树都需要依赖准备。
- 设计比较：共享整个 `node_modules` 的符号链接会造成生命周期脚本、平台二进制和分支依赖互相
  污染；自动扫描 package manager 会引入隐式行为；选择项目显式声明
  `worktree_setup_commands`，以 `pnpm install --offline --frozen-lockfile` 复用本机 store。
- 执行边界：本地文件完成后、CodeGraph 前按 argv 执行，不经 shell；离线缓存缺失、可执行文件
  缺失或非零退出均阻断 binding，不自动改为联网安装。审计只记录命令序号、可执行文件和退出码，
  不记录 stdout、stderr 或环境变量。
- 相同配置已经成功准备且 binding 为 active 时不重复 install；配置变化或 blocked 重试时重新执行。
- 真实补齐时发现当前 MOM 需求已在 `verifying`：旧检查在解析已有 binding 前拒绝所有重入。
  调整为 verifying 只可重新激活已有 active/blocked/initializing binding，仍禁止首次创建工作树。
- 用户只批准本轮实现与当前 MOM Web 工作树初始化；未批准测试、lint、类型检查或质量复核。
- 当前 MOM Web 初始化按设计失败并保持 blocked。首个 pnpm 11 错误是锁文件要求
  `autoInstallPeers=false`；显式匹配该设置并使用项目指定的缓存 pnpm 10.22.0 后，冻结安装继续
  报 `ERR_PNPM_LOCKFILE_MISSING_DEPENDENCY`，缺少
  `vue-draggable-plus@0.6.1(@types/sortablejs@1.15.9)`。这属于业务仓库锁文件缺陷，不能由 Praxis
  静默执行 `--no-frozen-lockfile` 修复；MOM Web 命令已登记该配置参数，等待业务锁文件单独修复。

## 22、第七轮 Fork 可见命名调查（2026-07-21）

- 当前需求父目录已经包含需求 ID 和简称，但 Fork 的 Worktrees 只显示末级 `web`，Branches
  只显示 `REQ-20260721-003`，因此用户无法从两处第一眼识别需求语义。根因不是聚合层级，
  而是末级目录和分支丢失了同一组可读字段。
- 保留需求父目录聚合；末级目录改为 `<REQ-ID>__<固定简称>__<repository_id>`，分支改为
  `praxis/<REQ-ID>__<固定简称>`。内部 identity 仍为 `WT-<REQ-ID>--<repository_id>`。
- `RequirementPathPolicy` 已把简称限制在 4–24 字符；工作树命名再清理 Git ref 禁止字符、
  `..`、`@{` 和 `.lock` 后缀，需求 ID 永不截断，并用 `git check-ref-format` 做最终门禁。
- 首次生成的简称快照写入 `worktree_group`。后续显式修改需求标题不会自动漂移同需求其他仓库；
  遗留 binding 优先从已有需求父目录恢复原简称，而不是套用当前标题。
- 比较方案：按仓库平铺会破坏多仓库需求聚合；依赖 Fork 自定义显示名没有跨客户端保证；因此采用
  目录和分支自身可读的方案。
- 正式迁移命令按仓库执行 Git worktree move、当前分支重命名、binding/产出物路径更新和
  CodeGraph 路径重建；失败执行补偿回滚，回滚不完整时 binding 必须 blocked 并留下审计。
- 本轮未获测试、lint、类型检查或质量复核批准，只执行结构、配置和 Git 名称安全检查。
