# 调查分析

## 1、需求目标

将 Praxis 的多仓需求准备从“所有治理动作串行完成后才开发”调整为“Git 隔离与 binding 激活后立即可开发，重型治理后台化”，同时保留安全、审计和人工批准边界。

## 2、业务背景

实际 MOM/AOTU 流程中，业务编码不是主要耗时项。工作树二次改名、三仓 CodeGraph 串行重建、binding 从 blocked 补激活、Web 离线依赖失败和产出物重复登记才是主要瓶颈。已观测到单仓 CodeGraph 约 55–379 秒，远高于 Skill 扫描的约 0.01 秒。

## 3、当前实现

- `WorktreeService.create_for_requirement` 先同步模板分支、创建 Git worktree，随后同步执行本地文件复制、全部 setup 命令和 CodeGraph 初始化。CodeGraph 失败会把 binding 标为 blocked。
- `migrate_name` 会在 Git 路径/分支迁移后同步重建 CodeGraph，且恢复迁移前状态；如果旧状态为 blocked，迁移成功仍保留 blocked。
- 需求状态机不允许 `verifying -> in_progress`，只能先 blocked 再恢复。
- `ArtifactService.add` 每次生成新 ID，没有按“需求+规范路径”去重或刷新哈希。
- Skill 节点需 route、多次 invoke、多次 complete、gate；路由快，但命令往返和重复审计较多。
- AgentSession 已有上下文包和权限授权，但未显式生成 `fork_turns=none` 的精简交接建议，也未固化“父节点单写状态”。

## 4、涉及业务域

- `plugin-development`

## 5、涉及系统和仓库

- 系统：`praxis-next`
- 仓库：`praxis-next` Python 插件

## 6、涉及模块

- `worktree`：命名预览、ensure、并行 Git、延迟 setup、binding 状态、迁移恢复。
- `codegraph`：持久化队列状态、后台 worker、显式等待/查询。
- `knowledge/domain/storage`：reopen、批准收据、阶段证据与重试预算。
- `artifacts`：稳定键 upsert 和哈希刷新。
- `skills`：节点批处理、路由缓存、预算单位显式化。
- `agents`：精简交接包、父节点回执和单写约束。
- `application/cli/mcp/guidance`：对外命令和指导文档同步。

## 7、业务规则

1. 工作树仅在确认需改代码时创建；创建前必须先预览最终名称，一次创建。
2. Git worktree 存在、本地白名单文件就绪且 binding active 即可编码；CodeGraph 和依赖安装不再是 active 前置。
3. CodeGraph 失败只影响语义图谱能力，不取消 Git 工作树的可开发状态；查询时才显式等待或回退 `rg`。
4. 依赖安装默认 deferred；preflight 只做快速、无网络、无脚本、不修改锁文件的可用性检查。
5. `migrate-name` 交易成功即恢复 active；旧 blocked 原因作为审计信息保留，不传播为新迁移结果。
6. `requirement reopen` 只允许从 verifying 审计化回到 in_progress，必须给出原因。
7. 产出物的稳定唯一键为 requirement_id + 规范化绝对路径；重复 add 刷新类型、阶段、元数据、大小和哈希，保留 artifact_id/created_at。
8. 批处理 Skill 不得绕过安全边界；approval_required 仍需已存在的明确批准收据。
9. 默认每阶段证据有预算，同一 operation key 最多一次恢复、一次重试；超限时返回可解释状态。

## 8、数据口径

- 耗时使用 `monotonic` 计时，以毫秒写入审计明细，不把 stdout/stderr/环境变量写入耗时事件。
- CodeGraph 状态区分 queued/running/completed/failed/stale，binding 状态与图谱状态解耦。
- 批准收据按需求、scope、允许命令/验证矩阵和有效期保存，不从“继续/完成”等模糊语句推断。

## 9、接口与数据流

1. `worktree ensure --preview` 产生 preview_id 及所有最终名称。
2. `worktree ensure --confirm <preview_id>` 校验快照，并行执行各仓 Git 创建，复制白名单本地文件，激活 binding，后台排队 CodeGraph。
3. `worktree prepare` 在首次需要构建时显式执行 setup。
4. CodeGraph worker 持久化心跳和最终状态；查询可选 wait，否则返回建议 `rg` 的明确诊断。
5. `requirement reopen --reason` 原子更新需求状态并审计。
6. `artifact add` 内部先查找稳定键，命中则 upsert，未命中则新建。
7. `skill complete-node` 在 Agent 已真实使用 Skill 后，一次上报 used skill + outcome，内部完成路由、调用、完成和 gate 审计。

## 10、现有能力复用

- 复用 StateStore WAL、runtime_state 和链式审计，不新增外部队列/数据库。
- 复用现有 Worktrunk、CodeGraphService 心跳、RequirementProjector、ContextCompiler 和 MCP broker。
- 后台 CodeGraph 使用同一 Python 环境的小型 worker 进程，不引入 Celery/Redis。

## 11、代码图谱调查

本轮以 `rg` 和已有代码为主，没有等待 CodeGraph，正是待实现快速路径的预期用法。现有 CodeGraphService 已提供锁、心跳、恢复和元数据，可作为后台 worker 内核。

## 12、数据库调查

无业务数据库变更。Praxis 本地 SQLite 已使用 WAL 和 busy timeout，可支撑多仓并行状态写入；并行操作仍应保持单 binding 单写。

## 13、影响范围

- CLI/MCP 新增操作，现有命令保持兼容。
- 工作树的 active 语义从“Git+setup+CodeGraph 全完成”收窄为“Git+本地运行文件就绪”，这是主要行为变更。
- AGENTS.md/CLAUDE.md 管理区块需同步新流程，保留用户自定义内容。

## 14、风险分析

- 后台进程可能在宿主退出时中断：依靠现有 heartbeat/stale 恢复，状态不伪装 completed。
- 多仓并行可能部分成功：ensure 返回每仓结果，不删除已安全创建的工作树，重试仅处理未完成仓库。
- 延迟安装会将失败后移：preflight 提前检查项目版本、命令和锁文件基本一致性，真正安装失败只标记 setup failed，不破坏 worktree active。
- 批处理 Skill 可被误用为伪造完成：要求显式 `--used-skill` 和非空 outcome，并保留每个 Skill 独立事件。

## 15、待确认事项

无。用户已明确确认快速路径、四项 P0 优先级以及不得未批准执行质量复核/测试的边界。

## 16、调查证据

- Skill 扫描：31 个 Skill 约 0.0116 秒；MOM 项目 11 个业务 Skill 约 0.0101 秒。
- CodeGraph 审计耗时：MOM web 54.9 秒、backend 185.6 秒、mes-pda 379 秒；AOTU backend 108.4 秒。
- 单个 MOM in_progress 需求累计 4 次 route、14 次 invoke、17 次 complete、13 次 gate，说明命令编排可继续压缩。
- 现行代码证据：`worktree/service.py::_activate_binding`、`domain/requirement.py::_NEXT_STATUS`、`artifacts/service.py::add`、`skills/routing.py`、`agents/service.py`。

## 17、分析结论

采用“快速核心 + 后台治理”的兼容方案：现有单仓 `worktree create` 保留，新增 preview/ensure/prepare/reopen/批处理能力；将 setup 和 CodeGraph 从 binding active 前置中解耦，并以持久化状态、心跳、审计和显式等待保持可观测性。不引入新基础设施，不让快速路径绕过安全门禁。
