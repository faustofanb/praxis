# 调查分析

## 1、需求目标

修复 Praxis 需求约束易陈旧、实施与验证状态混合、业务 Skill 路由过宽、上下文包未自动生成或未被 Agent 消费，以及数据库连接事实在长流程中丢失的问题。MOM 特有的 Backend/MES_PDA 细则由独立需求 `REQ-20260722-003` 落地。

## 2、业务背景

MOM 多仓需求依赖项目级 Skill、DBX 连接引用和隔离工作树。当前这些事实虽然存在于 `praxis.toml`、系统画像和手动 context bundle 中，但没有形成开发入口的自动数据流。

## 3、当前实现

- `context build` 只能显式调用，`worktree ensure`、`task start` 和 `agent start` 不负责生成。
- `agent start` 强制调用方预先提供 context ID；render 只写 ID、路径和 `handoff.json`，launch 命令没有初始提示要求读取正文。
- 数据库连接只位于优先级 1 的系统画像片段；画像缺失、陈旧或 Token 预算不足时可能不进入上下文。
- `context_current` 缓存键只包含需求、stage、role，没有 project、workflow node 和 intent。
- 项目业务 Skill 的 `triggers` 未参与 `route_context`；专项 Skill 在无关 intent 下也会加载。
- 外部 Skill 只扫描 `.codex`、`.agents`、`.claude`，没有扫描当前已安装 SkillDock 的 `.skilldock/skills`。
- `需求总览.md` 的“当前结论”每次投影都回到“待调查”，缺少可机读的生效约束和 `supersedes` 关系。
- 需求只有单一线性 `status`，代码已实现但验证未授权时无法诚实表达。
- 已有 approval receipt 可做精确验证矩阵，但没有计划阶段的固定入口，也没有用户明确拒绝/豁免验证的收据。

## 4、涉及业务域

Praxis 工作流治理、上下文工程、Skill 路由、DBX 安全调查。

## 5、涉及系统和仓库

- 系统：`praxis-next`
- 仓库：`praxis-next`（Python plugin）

## 6、涉及模块

Requirement service/projector、approval/verification receipt、Skill registry/router、context compiler、worktree application orchestration、Agent session adapter、CLI、Agent guidance 和 DBX Skill。

## 7、业务规则

- 项目基础业务 Skill（ID 以 `.development` 结尾）按 project 自动加载。
- 项目专项业务 Skill 同时满足 project 与 intent trigger 才加载；无 trigger 的 Skill 保持项目级加载。
- 工作树 ensure 成功后必须为每个成功项目生成 coder context，并在结果中返回关键事实和路径。
- Agent 未显式提供 context 时必须从 binding 推断项目并自动生成或复用；显式 context 继续兼容。
- 数据库连接引用、生产连接标记和显式选择规则是 P0，不依赖画像且不得被预算淘汰。
- 任何数据库结构或数据调查都必须先明确 DBX connection，并用 `current_database()` 核对实际数据库。
- 需求约束必须结构化记录；新结论可显式覆盖旧结论，仅 active 约束进入当前结论和 P0 上下文。
- 实施状态、验证状态和人工验收状态分开记录；`implemented` 不等于 `verified`。
- 计划确认时保存精确验证矩阵；明确不执行时保存 decline receipt，但不得投影为“验证通过”。
- 接口契约冻结和单筐纵向闭环是由任务意图触发的条件式 Skill，不是所有需求的强制门禁。

## 8、数据口径

上下文仍存储在现有 `context`、`context_current` 状态和 `生成内容/上下文包` Markdown 中。新增 `critical_facts` 只是同一上下文的紧凑投影。需求约束、交付状态和验证 decline receipt 使用现有 `runtime_state` 与审计链，不修改已执行迁移。

## 9、接口与数据流

`requirement constraint add` → 原子标记被覆盖约束 → 投影当前有效约束/决策历史；`requirement record-implementation` 与 `verification decline` 分别更新实施和验证维度。`worktree ensure` → 对成功 repository 调用 `ContextCompiler.build` → 返回 `context_bundles`；`agent start` 无 context ID → 从 binding 获取 repository ID、路径范围和阶段 → 调用相同 compiler → render handoff → launch 初始提示要求先读取 handoff 与 context。

## 10、现有能力复用

复用 `ContextCompiler` 的去重、脱敏、预算、指纹和审计；复用 `WorkspaceService.project` 读取 DBX 引用；复用 worktree binding 提供 project 与允许路径。

## 11、代码图谱调查

使用 `rg` 追踪 `ContextCompiler`、`AgentSessionService`、`WorktreeService.ensure_for_requirement`、`SkillRegistry.route_context` 和 CLI 映射。未使用 CodeGraph。

## 12、数据库调查

本需求不查询业务数据库。代码证据确认 project 配置已经区分普通 `database_connections` 与 `production_database_connections`，但 context 没有将其作为 P0 直接注入。

## 13、影响范围

改变需求投影、交付状态表达、业务 Skill 选择、worktree ensure 返回体、Agent start 默认行为、Agent launch 命令和上下文内容。保留显式 `context build` 与显式 `--context` 的兼容路径。

## 14、风险分析

- 自动生成失败发生在工作树已创建之后：返回明确的 context failure 和已创建 binding，不回滚安全的 Git 工作树。
- 基础业务 Skill 被错误过滤：仅对非 `.development` 且声明 triggers 的专项 Skill 启用 intent 过滤。
- context 内容过大：只把紧凑 `critical_facts` 放进命令结果和 handoff，完整正文仍在 Markdown。
- 多仓缓存串扰：缓存键和指纹均包含 project、workflow node 与 intent。
- 结构化投影覆盖人工文字：新增受管的只读约束/状态区块，不改写调查、计划和验收正文。
- 过度扩大通用门禁：契约冻结、单筐闭环和 MOM 细则仅在项目+意图命中时路由。

## 15、待确认事项

无。用户已选择方案 2，不增加 `context consume` 收据门禁。

## 16、调查证据

- `src/praxis/context/service.py`：context 仅手动构建，数据库事实来自可选画像。
- `src/praxis/agents/service.py`：start 要求 context ID，launch 命令当前仅为 Agent 可执行文件。
- `src/praxis/application.py`：worktree ensure 直接返回 worktree service 结果。
- 实际 `route-node --project mes-pda --intent 调整页面卡片颜色` 仍加载 UniApp API 专项 Skill。
- `grilling` 位于 `.skilldock/skills`，当前路由扫描判定 unavailable。

## 17、分析结论

根因同时存在于“没有权威的当前约束”和“上下文生成、路由、Agent 启动之间没有闭环”，而非模型本身遗忘。采用方案 2：结构化约束与覆盖关系；分离实施/验证/人工验收；修正 project+intent 路由和 SkillDock 发现；把项目、有效约束、验证矩阵与数据库事实提升为 P0；在 worktree ensure 与 agent start 自动构建并强制传递。MOM 条件式细则在 `REQ-20260722-003` 中作为专项 Skill 安装。
