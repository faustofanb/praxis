# 调查分析

## 1、需求目标

praxis（Praxis V3）是面向 AI 编码代理（Codex、Claude Code 等）的工作流治理平台。本需求针对「praxis 对 AI 不够友好」的反馈，量化 AI 实际使用 praxis 时的认知负担（命令树、输出结构、错误码、上下文注入），识别首次接触与高频使用中的具体卡点，并输出分优先级的可落地优化方案。

## 2、业务背景

praxis 以「bounded AI development workflow」为定位：需求生命周期（captured → completed 共 9 节点）、Skill 路由/调用/门禁、worktree 绑定、fail-closed 状态流转、审计链。其"用户"主要是 AI 代理而非人类；AI 每会话通过 AGENTS.md/CLAUDE.md 静态注入 + Skill 按需加载 + MCP 工具/CLI 命令与平台交互。友好的标准是：AI 能以最低学习成本正确完成工作流步骤，遇阻时能自愈而非卡死。

## 3、当前实现

- 入口：CLI（`praxis`）+ MCP server（约 120 operations）共享 `PraxisApplication.execute` 分发表，行为一致。
- 输出：统一结果包络 `{"ok", "code", "data", "diagnostics"}`；`--summary` 紧凑单行、`--json` 完整机器包络。
- 引导层：AGENTS.md/CLAUDE.md 受管块（REQ-20260817-001 已瘦身至约 55 行指针+不变式+表格）；内置 SKILL.md 按需加载。
- 状态机：9 节点，`requirement advance` 逐节点推进，全部 fail-closed；节点 Skill 门禁经 `skill route-node`/`invoke`/`complete` + `lifecycle complete-node` 原子提交。

## 4、涉及业务域

plugin-development（praxis 平台自身）。

## 5、涉及系统和仓库

- praxis-next（Python 插件，`codex/praxis-v3-development` 模板分支）。

## 6、涉及模块

- `src/praxis/cli/__init__.py`（命令注册、输出渲染、`_compact_payload`）
- `src/praxis/result.py`（结果包络与错误码）
- `src/praxis/skills/routing.py`（`NodeSkillRouter.policies()` 策略表）
- `src/praxis/agents/guidance.py`（受管块生成）
- 新增：`src/praxis/guides/`（方案 A 的任务导向引导）、错误码目录数据文件

## 7、业务规则

- 状态流转与 worktree create 均 fail-closed；当前节点缺少 route、完成凭证或 gate 时必须停止。
- 节点 Skill 门禁按 `node-routing.toml`（24 providers，4 种 mode）逐节点判定。
- 输出契约：`ok/code/data/diagnostics` 是稳定机器包络，MCP 与 CLI 共用。

## 8、数据口径

- 命令树广度：顶层 28 命令；requirement 16、skill 15、worktree 11、lifecycle 10 子命令，合计约 60+。
- 错误码集合：源码 `Result(False, "<CODE>")` 约 100 个（抽样统计前 50：REQUIREMENT_NOT_FOUND ×24、WORKTREE_BINDING_INVALID ×5、USER_APPROVAL_REQUIRED ×5、RTK_NOT_AVAILABLE ×5 等）。
- 上下文注入：AGENTS.md 77 行、CLAUDE.md 77 行；受管块约 55 行正文；节点策略表注入全部 24 providers。
- 内置 Skill：10 个，praxis-requirement-workflow 188 行、minimum-module-compile 150 行等。

## 9、接口与数据流

- AI → MCP/CLI → `PraxisApplication.execute` → 各服务 → 结果包络。
- 引导层：`AgentGuidanceService._managed_content` 同时渲染 AGENTS.md 与 CLAUDE.md。
- 错误：各服务返回 `Result(False, code)` → CLI/MCP 渲染包络（`diagnostics` 常为空数组）。

## 10、现有能力复用

- `--summary`/`--json` 双档输出机制（方案 C 扩展 `_compact_payload`）。
- `praxis doctor --json` 入口诊断（方案 A 的 guide 可引用其状态）。
- REQ-20260817-001 的去重手法（受管块瘦身、SKILL 唯一权威源）可延续到方案 D。
- 错误码集中在各服务 `Result(False, ...)`，可静态抽取登记 catalog。

## 11、代码图谱调查

改动面集中于 CLI 输出层、新增 guide 子命令、错误目录数据、路由策略过滤，无事务、锁、原生 SQL、并发、共享服务或高扇出改动；不触发 `codegraph-impact-analysis` 强制门禁（无公共接口/结构迁移变更；错误码集合本身不变，只新增查询入口与渲染）。

## 12、数据库调查

不涉及。方案均为 CLI/输出层新增，无 DBX 连接、结构或数据变更。

## 13、影响范围

- praxis-next 自身新增 CLI 子命令（guide、errors）与输出增强；无破坏性变更。
- 错误码集合不变，`ok/code/data` 契约保持，`--json` 输出不变（方案 C 只裁剪非 `--json` 默认渲染）。
- MCP operations 不变；mom/aotu 等下游仅受受管块指针影响（无强制）。
- 既有测试：聚焦 `tests/test_interfaces.py`（CLI 映射）、`tests/test_application_dispatch.py`（分发表）、`tests/test_agent_guidance.py`（受管块）。

## 14、风险分析

- 方案 C 裁剪默认输出若误改 `--json` 契约会破坏机器消费：缓解 = 契约只由 `--json` 保证，默认渲染独立于契约字段。
- 方案 D 策略表过滤若漏掉 required provider 会破坏门禁：缓解 = 过滤只发生在「展示层」的 AGENTS 注入，`NodeSkillRouter` 判定逻辑不改；按 system 过滤后对命中的必需 provider 全量保留。
- 方案 A/B 为纯新增，风险低；方案 E 为错误消息渲染增强，风险低。
- 错误码 catalog 需人工核对含义，工作量集中在文案，可在同一需求内分批完成。

## 15、待确认事项

- 优化范围：用户是否只做 A+B（引导+错误自助，低风险高收益），还是含 C/D（输出与上下文裁剪，涉及契约/策略完整性复核）。
- 文案语言：中文提示与命令输出是否全部中文（当前 help 为英文）。

## 16、调查证据

- 命令树：`praxis --help` / `praxis requirement --help` / `skill` / `worktree` / `lifecycle` 实测计数（28 顶层 + 约 60 子命令）。
- 错误码：`rg -o 'Result\(False, "[A-Z_]+"'` 源码抽样（REQUIREMENT_NOT_FOUND 等约 100 个）。
- 输出包络：`praxis requirement advance REQ-NONEXIST --summary` 实测返回 `{"ok": false, "code": "REQUIREMENT_NOT_FOUND", ...}`（无 hint/next_step）。
- 上下文：`wc -l AGENTS.md CLAUDE.md`（各 77 行）；`NodeSkillRouter.policies()` 注入 24 providers。
- Skill 清单：`ls skills/`（10 个内置）+ SKILL.md 行数统计。

## 17、分析结论

praxis 对 AI 不友好的核心是「认知负担」而非「功能缺失」：命令树广（60+ 命令、英文 help）、错误码哑（约 100 个无解释无恢复建议）、默认输出含运行时噪音、节点推进仪式感强且 gate 阻断无补齐指引。优化方向以低风险输出层为主（方案 A 任务导向引导、B 错误自助、E 节点恢复指引），辅以输出/上下文裁剪（C/D），不改状态机与门禁，不破坏 MCP/CLI 契约。建议先实施 A+B，C/D/E 视授权分批。
