# 调查分析

## 1、需求目标

让 Claude Code 会话（无论是 praxis-next 自身的开发会话，还是 mom/aotu 等业务工作空间的会话）
能够真正发现并使用 Praxis 的 Skill 目录，并让委派子会话与根会话具备可工作的 PreToolUse
守卫，而不是只停留在 CLAUDE.md 的文字约定上。

## 2、业务背景

praxis-next 是 Praxis V3 平台自身的开发仓库；mom（IFC-MOM）与 aotu（AOTU）是通过全局安装的
`praxis`（uv tool，包名 `praxis-workflow`）使用同一套引擎的两个实际生产业务工作空间。三者共享
同一套 Skill 路由/生命周期引擎，但"引擎认为可用"和"Claude Code 实际能调用"是两回事。

## 3、当前实现

- `NodeSkillRouter._installed_skills`（src/praxis/skills/routing.py:369-390）扫描
  `~/.codex/skills`、`~/.agents/skills`、`~/.claude/skills`、`~/.skilldock/skills` 四个全局目录
  判定"已安装"；`skill_inspect`/`skill route-node` 额外能解析当前工作空间自身目录下的
  SKILL.md（如 praxis-next 的 `skills/*`），已现场验证（本需求 investigating 节点路由
  `route_fingerprint=2fd74c9c...` 五个技能全部 `status:available`）。
- 没有任何命令把技能部署到 Claude Code 实际会扫描的路径。`SkillCandidateService.promote()`
  （candidates.py:47+，对应 `skill approve`）只写入调用方传入的 `--catalog-root`，不涉及全局或
  项目级 Claude Code 目录。
- `AgentSessionService._json_config`（agents/service.py:317-362）为
  `agent start --type claude-code` 渲染 `hooks.{PreToolUse,PostToolUse,Stop}`，但 JSON 形状是
  扁平的 `{"PreToolUse":[{"command":...}]}`，不是 Claude Code 实际要求的
  `{"matcher":...,"hooks":[{"type":"command","command":...}]}`；且渲染出的
  `生成内容/Agent配置/<session>/claude-code.json` 从未被复制/合并进任何
  `.claude/settings*.json`，`launch()`（service.py:194-253）调用 `claude` 时也没有传
  `--settings`。
- 根交互会话没有等价机制：praxis-next 根目录没有 `.claude/settings.json`；mom 有一个手写的
  `.claude/hooks/check-praxis-binding.sh`（PreToolUse 守卫，逻辑正确：按 `praxis.toml` 里的仓库
  列表阻止未绑定 worktree 的 Edit/Write/`git commit`），但同目录的
  `.claude/settings.local.json` 只有 `permissions.allow`，完全没有引用这个 hook 脚本——脚本是
  死代码。aotu 连这个脚本都未创建。
- mom/aotu 均无 `.mcp.json`；`praxis` 从未作为 MCP server 注册（与 codegraph/dbx/tolaria 不同，
  这三者在 `~/.claude.json` 里都有对应条目）。

## 4、涉及业务域

plugin-development（praxis-next 自身）；下游应用覆盖 mom、aotu 两个 IFC-MOM/AOTU 制造运营业务域
工作空间的集成配置层（非业务代码）。

## 5、涉及系统和仓库

- praxis-next（本仓库，`python-plugin`）
- mom：`/Users/fausto/Desktop/workplace/project/ifc/mom`（`knowledge_root=knowledge`，7 个业务
  子仓库 + docs）
- aotu：`/Users/fausto/Desktop/workplace/project/ifc/aotu`（`knowledge_root=knowledge`，6 个业务
  子仓库 + docs）

## 6、涉及模块

`src/praxis/skills/`（新增部署逻辑）、`src/praxis/agents/`（复用 guidance 渲染风格）、
`src/praxis/cli/__init__.py`（新增 CLI 子命令）、`src/praxis/workspace/service.py`
（读取仓库列表用于生成 hook 脚本）。

## 7、业务规则

不修改任何业务仓库（ifc-mom-column-max 等）内部代码；只在三个工作空间的根目录写
`.mcp.json`、`.claude/skills/*`（符号链接）、`.claude/settings.local.json`
（合并 `hooks` 键）、`.claude/hooks/*.sh`、`.gitignore`（追加派生路径），且必须是合并写入而
非覆盖已有内容（mom 已有 `permissions.allow`、`.mcp.json` 若已存在其他 server 也不得清除）。

## 8、数据口径

不涉及数据库。

## 9、接口与数据流

无对外接口变更；新增一个 CLI 操作 `workspace install-claude`，输出结构与其他 Praxis 命令一致
的 `{ok, code, data, diagnostics}` 信封。

## 10、现有能力复用

- 技能发现复用 `NodeSkillRouter._installed_skills` 已验证的 `rglob("SKILL.md")` 扫描模式，
  作用域改为工作空间根目录（同时排除 `.git`/`node_modules`/`.worktrees`/`dist`/`.claude`）。
- PreToolUse 守卫复用 mom 现有 `check-praxis-binding.sh` 的判定逻辑，泛化为按
  `praxis.toml` 的 `systems.repositories` 动态生成仓库列表，而不是为每个工作空间手写一份。
- `.mcp.json` 内容复用 praxis-next 自身已验证可用的形状（`command: praxis`,
  `args: ["--root", "<workspace>", "mcp", "serve"]`），只是 mom/aotu 使用全局 `praxis`
  而非 `uv run --project`。

## 11、代码图谱调查

改动集中在 CLI/skills/agents 三个小模块的新增函数，无事务、锁、原生 SQL、并发或跨模块共享服务
调用，不满足 `codegraph-impact-analysis` 的强制触发条件（无高扇出、无公共接口变更）。

## 12、数据库调查

不涉及。

## 13、影响范围

praxis-next 自身新增代码（无破坏性变更，纯新增 CLI 子命令）；mom/aotu 只新增/合并配置文件，
不触碰其 7 个业务子仓库的任何代码。

## 14、风险分析

- **未验证风险（需新会话确认）**：Claude Code 是否真的按约定扫描项目级 `.claude/skills/`
  目录——本会话开始时的技能可用列表已固定，无法在同一会话内自证；本需求的验证矩阵把这一项
  标为"需环境"而非"可自动化"。
- 符号链接稳定性：`uv tool list` 确认 `praxis-workflow` 的托管路径为
  `/Users/fausto/.local/share/uv/tools/praxis-workflow`，`uv tool install --reinstall` 只替换
  该路径下内容，不改变路径本身，符号链接可在重装后继续有效。
- `.gitignore` 缺口：mom/aotu 当前 `.gitignore` 未排除 `.claude/`，新增的符号链接和生成产物有
  被意外提交的风险，需要在写入前一并追加忽略规则。
- mom 的 `.claude/settings.local.json`、aotu 的同名文件目前只有 `permissions.allow`；合并写入
  `hooks` 键时必须用 JSON 层面合并，不能整体覆盖。

## 15、待确认事项

- `.claude/skills/` 项目级发现的真实行为——留待用户在新会话里验证（见验证矩阵）。

见对话记录与本文件第 3 节引用的具体文件路径/行号；mom 侧证据另见
`/Users/fausto/.claude/projects/-Users-fausto-Desktop-workplace-project-ifc-mom/memory/praxis_integration_audit_20260808.md`

Code 原生发现、无 hook 兜底）。

## 17、分析结论

三处集成缺口证据充分且集中在明确的代码位置，无需进一步调查；直接进入计划阶段。
