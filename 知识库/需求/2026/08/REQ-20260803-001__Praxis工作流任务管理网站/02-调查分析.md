# 调查分析

## 1、需求目标

新增 `praxis web` 本地工作流驾驶舱。看板以 `REQ-*` 需求为唯一主卡，直接聚合 Praxis 现有生命周期、Skill 路由/调用、上下文、工作树、门禁、产出物、审计和 Agent runtime；不创建独立子任务或第二套进度模型。

## 2、业务背景

当前 Praxis 能力分散在 CLI、Application、Broker 和 runtime_state 中，需求阶段、门禁和 Agent 会话需要通过多个命令查看。网页只提供固定的本地 API 和显式操作入口，保留 Praxis 作为状态与权限唯一来源。

## 3、当前实现

- `RequirementService` 已负责需求文档、阶段迁移、执行进度和重开。
- `StateStore` 只使用 `runtime_state`、`requirements`、`outbox`、`audit_events`，可继续保存聚合所需运行态，不新增表。
- `McpBrokerService` 已有按角色能力授权和需求/工作树范围校验，但需求级写入与 Agent 外部能力边界需细化。
- `ContextCompiler`、`WorktreeService`、`SkillInvocationService`、`ArtifactService`、`AgentSessionService` 可作为 Web 业务层的复用入口。
- `PraxisApplication` 是现有操作分发边界，Web 路由不能接受任意 operation、SQL 或进程参数。

## 4、涉及业务域

- `plugin-development`

## 5、涉及系统和仓库

- 系统：`praxis-next`
- 仓库：当前 Praxis V3 Python 插件仓库，使用独立 worktree 实施。

## 6、涉及模块

`knowledge.requirements`、`storage.sqlite`、`mcp.broker`、`application`、`agents.service`、`context.service`、`worktree.service`、`skills.routing`、`artifacts.service`、CLI、Python 标准库 HTTP server 及静态资源。

## 7、业务规则

1. 生命周期固定为 `captured → investigating → analyzed → planned → ready → in_progress → implemented → verifying → completed`。
2. 进度由阶段索引计算：`captured=0%`、`completed/archived=100%`；`blocked` 使用最近一次迁移审计的 `from` 阶段，旧审计无来源时返回未知进度。
3. 看板分为待开始、进行中、已阻塞、已完成四列；页面只能用“下一步”逐阶段推进。
4. 需求创建、阶段迁移、重开、追加进度是需求级写入，不要求工作树；上下文、工作树准备、门禁和产出物访问必须绑定需求与工作树。
5. Agent 只允许 `codex`、`claude-code`、`oh-my-pi`；网页启动/停止需要单一角色、显式 launch 开关和一次性确认令牌，进程归属校验失败即拒绝。
6. 服务仅监听 `127.0.0.1`，使用 HttpOnly/SameSite=Strict Cookie 并校验同源 Origin；固定 API 不透传任意操作。

## 8、数据口径

需求状态、执行进度文档和审计链是阶段与进度的唯一事实来源。Dashboard 仅构建读模型，关联的 Skill、上下文、工作树、产出物和 Agent 记录来自已有 runtime_state scope。不存在的截止日期、优先级和独立子任务不在界面展示。

## 9、接口与数据流

浏览器 → 本地 Web `SessionHandler` → 固定路由映射 → Web Broker 会话 → `McpBrokerService` 固定 capability → 现有 Praxis service / StateStore。所有响应使用 `Result` envelope；失败返回原始 code、diagnostics 和门禁缺口。

## 10、现有能力复用

复用 `RequirementService` 的 create/show/progress/advance/reopen、`NodeSkillRouter`/`SkillInvocationService`、`ContextCompiler`、`WorktreeService` 的 preview/ensure/prepare、`GateEngine`、`ArtifactService`、`AgentSessionService`、`StateStore.audit` 和现有角色 capability 集合。

## 11、代码图谱调查

本需求已在 `investigating` 节点路由并完成 `codegraph-impact-analysis`。高风险入口为 `PraxisApplication._execute`、`McpBrokerService.grant/invoke/authorize`、`AgentSessionService.start/launch/finish/receipt`、`StateStore.transition_requirement` 和 CLI parser；实现前需在隔离工作树完成新鲜 CodeGraph status/wait/ensure-fresh 与调用链查询。

## 12、数据库调查

不新增数据库表或 SQL 写入接口。仅复用 `runtime_state` JSON；需为迁移审计补充可靠的 `from` 阶段信息，并为 Dashboard 提供按需求过滤审计、需求和 runtime scope 的读取方法。

## 13、影响范围

影响 Web/CLI/API 分发、Broker 权限模型、需求审计投影和 POSIX Agent 进程生命周期；静态资源不引入 React、Vite 或额外运行时依赖。需要保持既有 CLI、MCP server 和 Agent 测试兼容。

## 14、风险分析

- 权限绕过：固定路由、能力白名单、需求/工作树绑定和同源保护共同约束；拒绝任意 operation。
- 进程误杀：只根据记录的 Agent session、PGID、命令和工作树校验，无法确认时 fail-closed。
- 状态错读：blocked 无 `from` 审计时不猜测进度；门禁失败不改变状态。
- 兼容性：新增字段保持 JSON 向后兼容，静态资源通过包数据配置发布。
- 并发：preview 使用指纹与过期时间；ensure 必须校验 preview 未过期且未变化。

## 15、待确认事项

产品范围已由用户确认；实现中不再引入截止日期、优先级、独立子任务、远程访问或部署能力。完整 pytest、ruff、ty、质量复核和浏览器手工验证仍按计划单独授权。

## 16、调查证据

- `src/praxis/application.py`：现有 requirement/skill/context/worktree/gate/agent 分发。
- `src/praxis/mcp/broker.py`：现有 capability 风险、角色权限和范围授权。
- `src/praxis/knowledge/requirements.py`：阶段迁移、推进门禁和执行进度文档。
- `src/praxis/storage/sqlite.py`：runtime state 与审计事件存储。
- `src/praxis/agents/service.py`：Agent 白名单、prepare/render、launch、finish、receipt。
- `tests/test_broker_agents_artifacts.py`、`tests/test_application_dispatch.py`：现有契约测试与可复用 fixture。
- Praxis 调查节点审计：`AUD-20260803T094653-BB31C8C0`。

## 17、分析结论

采用“薄 Web 适配层 + 固定 Broker capability + 现有 Praxis services”的最小实现。先在隔离 worktree 补充 RED 测试，再实现 Dashboard 聚合、权限边界、Agent 控制、CLI 和静态页面；不改变 Praxis 的数据模型，不创建网页专属业务状态。
