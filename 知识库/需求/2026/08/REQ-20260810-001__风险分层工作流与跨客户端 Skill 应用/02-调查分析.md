# 调查分析

## 1、需求目标

将 Praxis 从“所有需求都走同一套重治理”优化为按风险分层的三档工作流，并把 Praxis 的治理能力与 Matt Pocock 等工程 Skill 清晰分工；为 Codex 与 Claude Code 提供可审计、可重复的 workspace 应用入口。

## 2、业务背景

Praxis 应保留需求知识库、Worktrunk 隔离、DBX/CodeGraph 安全、状态与审计；工程设计、实现、调试和测试方法交给已安装的外部 Skill。低风险任务不应被 TDD、最小编译、review 等门禁拖慢，高风险任务不能因为进入 fast/small profile 而绕过审计。

## 3、当前实现

- `FastLaneService` 提供 `fast start/confirm/red/finish`，已具备低风险缺陷的 reproduction、RED/GREEN、diff-check、增量 typecheck 和 artifact 记录。
- `SmallFixService` 提供 `fix start --small/finish`，限制单仓库、1–3 个业务文件和 80 行变更。
- `FastFixService.record` 提供单文件微改的 direct/declined verification 登记。
- `NodeSkillRouter` 支持 standard、fast-defect-v1、small-fix-v2，但两个轻量 profile 会过滤非 core Skill；标准 CodeGraph policy 的风险集合与 Fast/Small 的禁止集合不一致。
- Fast/Small 会持久化 route，但 finish 没有复用 `SkillInvocationService.complete_node/gate` 形成结构化完成证据。
- Claude 有 `workspace install-claude`，能合并 MCP、链接 workspace Skills、安装 binding guard；Codex 没有对等 workspace apply 命令。
- `AGENTS.md` 与 `CLAUDE.md` 由同一 managed block 生成；`.codex-plugin/plugin.json` 声明 skills/MCP，`.claude-plugin/plugin.json` 仅有元数据。
- 路由器只发现已安装的 `~/.codex/skills`、`~/.agents/skills`、`~/.claude/skills`、`~/.skilldock/skills`，项目不应自动联网安装第三方 Skill。

- `praxis.cli` 与 `praxis.application`
- Codex/Claude plugin manifests 与 workspace guidance

## 7、业务规则

1. 未命中高风险且边界明确的任务才可进入 fast/small。
2. 事务、锁、并发、原生 SQL、schema/migration、公共 API、共享代码、跨模块、高扇出、权限和生成代码等命中项必须回到 standard，并保留 CodeGraph/DBX 等命中门禁。
3. Fast/Small 降级必须 fail-closed，并返回明确的 standard handoff，不删除既有审计或绑定。
4. 客户端应用只投影本地已存在且经允许的 Skills；缺失 provider 只报告，不联网下载。
5. Codex 与 Claude 共享 MCP 与 guidance 语义；客户端能力不同的 hook 不得伪造为等价。
6. `agent install` 是 session adapter 生成，不等于 workspace client install/apply。

## 8、数据口径

- 风险以稳定的 canonical id 保存，输入别名只在边界归一化。
- Skill 应用结果至少包含 source、path、content hash、target、linked/skipped/missing。
- Lane handoff 至少包含当前 lane、目标 standard lane、命中的风险和下一步操作。
- 既有 artifact、approval、audit 记录不因降级或重复调用而重复创建。

## 9、接口与数据流

`workspace install-agent` → 读取 workspace/project 与已安装 Skill 目录 → 写入客户端可发现的 MCP/Skill/guidance 配置 → 记录投影结果与 audit。

`fast/small route` → canonical risk eligibility → low-risk profile route 或 standard handoff；finish → 验证 → structured Skill completion/gate → artifact/implementation。

## 10、现有能力复用

- 复用 `ClaudeIntegrationService` 的 JSON merge、symlink 冲突保护、hook、`.gitignore` 和 audit。
- 复用 `AgentGuidanceService.render` 的 managed block 更新。
- 复用 `NodeSkillRouter.route` 的 fingerprint/cache/provider diagnostics。
- 复用 `SkillInvocationService.complete_node(..., structured=True)` 与 `gate()`。
- 复用 `FastLaneService` 的 worktree、baseline、artifact 和 downgrade 机制。

## 11、代码图谱调查

本仓库没有 `.codegraph/` 索引；按项目规则未初始化索引。已通过源码调用路径调查：CLI → `PraxisApplication._execute` → Fast/Small/ClaudeIntegration 服务；普通标准 lane 由 `NodeSkillRouter` 与 `SkillInvocationService` 承担门禁。当前需求不涉及数据库或生产连接。

## 12、数据库调查

不涉及数据库结构、数据或 DBX 查询。

## 13、影响范围

核心影响集中在风险路由、两个轻量 lane、workspace client integration、CLI/application dispatch、测试和 README。不得修改 MCP broker、Worktrunk 实现或其他客户端行为；保留 `.codex-plugin/plugin.json` 的现有用户修改。

## 14、风险分析

- 最高风险是 Fast/Small 过滤 CodeGraph 后造成高风险变更漏审；通过共享 taxonomy 和 profile eligibility fail-closed 消除。
- Skill gate 接入若破坏既有幂等，将导致重复 invocation/artifact；必须以已有 gate service 和稳定 key 为准。
- Codex client hook 能力未与 Claude 完全对等；只实现实际支持的投影，使用 AGENTS/pre-commit/worktree guard 作为边界。
- 外部 Skill 安装涉及网络、来源和用户信任；本需求只应用本地已安装 provider，不自动下载。
- 当前工作树有 `.codex-plugin/plugin.json` 用户修改；实施采用需求 worktree 和精确变更检查，不覆盖该内容。

## 15、待确认事项

- Codex 当前版本实际读取的项目级 Skill/hook 配置字段需要以仓库现有 manifest 和本地客户端契约为准，不猜测未验证字段。
- Small-fix 不执行 RED，因此需要把其 required Skill 语义调整为 focused verification，而不是冒充完整 TDD。

## 17、分析结论

推荐先统一风险 taxonomy 和 lane eligibility，再接入 structured Skill gate/handoff；随后抽取 workspace client projection，新增 `workspace install-agent --agent codex|claude-code|all`，兼容 `install-claude`。该顺序先修安全边界，再扩展客户端应用，避免把安装便利建立在高风险漏审之上。
