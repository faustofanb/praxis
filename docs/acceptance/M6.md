## Failure Acceptance

- [x] extension cannot bypass core capability checks
  - **结构性（不靠自觉）**：`ToolHookDecision` 类型上只有 deny——"allow" 不可表达；伪造非 deny 返回是契约违规（`InvalidExtensionError`），与 failurePolicy 无关；`beforeTool` 组合在 capability authorizer **批准之后**（ADR-0007 顺序不变），authorizer 拒绝时扩展根本不被咨询。
  - `tests/security/extension-bypass.security.test.ts`（M6-T001，4 tests）：capability 拒绝先于扩展接缝（咨询计数 0、工具永不执行）；伪造 allow 抛契约违规；扩展 deny 与任何 veto 产生相同 ToolRejected 事实形状（事件序 Proposed→Rejected 无 Started）；默认只读策略对配合型扩展同样成立。37/37 含 M5 既有对抗面无回归。
  - **can-fail 证据（验收时实做，同上即还原）**：注入伪证断言"capability 拒绝后扩展仍被咨询（consulted===1）"→ `mise run test:security` exit 1（1 failed | 36 passed）；还原后 37/37。

## 设计—实现一致性（docs/07 §6）

- 是否新增 package？**是（即 M6 目的本身，ADR-0013 预先批准）**——`@praxis/extension-telemetry`、`@praxis/extension-standing-orders`，均为私有包、仅依赖 contracts、tier1 声明于 `.praxis/architecture.yaml`（`test:architecture` PASS 9 包）。注册路径（根 package.json devDependency 行、bun.lock 机械记录、tsconfig 引用）在 M6-T002 作为两次合同修订记录在案（scope_notes），M6-T003 起即预算内成本；dependencies 规则门（build+unit+knip）对 package.json/bun.lock 全绿。
- 是否新增 Core dependency？否——core 仍只依赖 contracts；两个扩展包不进入任何包的依赖闭（除测试引用）。
- 是否新增 durable contract？否——durable 事件词汇表零变更（schemaVersion 保持 1，迁移表保持空）；contracts 新增的 `extensions.ts` 是 hook 接缝契约（类型 + 校验），非事件词汇。扩展零事件写入（onEvent 只读，流恒等测试钉死）。
- 是否让 optional extension 承担 Core invariant？否——capability 执法在 core authorizer（beforeTool 组合其后、只收紧）；deny-only 类型不变量在 contracts（对所有实现者生效）；telemetry 只观察、standing-orders 只贡献/否决，均不承担 Core 不变量。
- 是否产生两个事实源或两个状态管理器？否——store 仍是唯一持久历史；扩展状态全在实例闭包（telemetry 快照是 in-memory 读数，standing-orders 配置冻结于构造）。
- 是否有系统设计已过期但本次没有更新？否——docs/02 §19 已具体化为 v1 法则（commit `d42c557`）+ §19 拒绝清单与 ADR-0013 一致；docs/03 M6 六行全部勾选并带出处；subsystem docs 三份（core 接缝条目 + 两个扩展包）+ 索引随任务同步。
